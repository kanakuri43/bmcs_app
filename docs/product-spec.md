# Product Spec

CLAUDE.md の要約から分割した、ドメイン仕様・業務フローの詳細。
優先順位は CLAUDE.md 側が正であり、本ファイルの内容と矛盾する場合は CLAUDE.md を優先する。


## UI/UX
MahApps.Metro と既存スタイルへ合わせる。
派手さより可読性・誤操作防止・状態の明確さを優先する。

特に:
- 画面操作全般は、マウスだけでなくキーボードでの操作を前提に設計する（マウスでしか完結しない操作を作らない）
- 日付は `YYYY/MM/DD` 表記で統一
- 金額・数量はカンマ区切り・右揃え、入力はカンマなし数値でblur時に自動整形
- `Tab` だけでなく `Enter` でも次項目へフォーカス移動（誤送信させない）
- 検索モーダル・明細一覧は上下矢印キーで行選択、`Enter` で確定・転記
- フォーカス中の入力欄は背景色を変えて視認性を上げる
- プリンタ設定はDB管理せず、`bmcs_config.json`（実行ファイルと同じフォルダ）へ端末ごとに保存する（P-4・2026-09-10確定、TODO.md 2-6で実装済み）
- **起動直後のフォーカス**: 画面表示直後は、伝票番号／マスタコードの入力欄にカーソルがある状態にする（例: 売上入力→売上No、入金入力→入金No、得意先マスタ保守→得意先コード）。伝票番号・コードを持たない画面（請求締め処理等）は、画面内で一番最初の入力フィールドにフォーカスを置く（2026-09-11確定）。
- **ジャーナル系画面の伝票No入力欄の挙動**（売上入力・受注入力・明細請求書発行・入金入力等、伝票Noを持つ画面共通。2026-09-14確定）:
  - 空欄のまま `Enter`: 新規登録モードとして、伝票No欄の次の入力欄（売上入力→売上日付、受注入力→受注日付、明細請求書発行→請求日付）へカーソル移動する。入力済みのデータは消さない。
  - 伝票Noを入力して `Enter`: その伝票No の伝票を呼び出し、空欄時と同じ「伝票No欄の次の入力欄」へカーソル移動する。ただし読込後に画面全体が読み取り専用表示になる画面（明細請求書発行の既存分読込等）は、移動先の入力欄が存在しないため伝票No欄にカーソルを留める。
  - 入力された伝票Noが存在しない場合はエラーを表示する（新規登録モードへは進まない。入力済みの得意先・明細等も破棄しない）。
  - `Space` キー押下で伝票検索ダイアログを表示する。
  - 対象は実装済みの4画面（売上入力・受注入力・明細請求書発行・入金入力。Phase 7-2実装により入金入力も対応済み、2026-09-15確定）。請求締め処理・締め解除処理は請求Noを扱うが新規登録モードの概念が無く対象外。
- **登録後のリセット**: 保存・登録処理が成功した後は「登録しました」的な完了メッセージを表示し、画面を起動直後の状態（新規入力可能な空の状態）に戻して、先頭項目へ自動でフォーカスを戻す（2026-09-11確定）。
- **リスト選択の確定操作**: 検索モーダル・明細一覧など、一覧からの選択操作は `Enter` キーによる確定を基本としつつ、ダブルクリックでも同じ動作（同じコマンド）を呼び出す（2026-09-11確定）。


## 共通業務ルール

1. **消費税・端数処理**: 得意先マスタの税区分（請求単位／伝票単位／内税明細単位）と端数区分（切捨／四捨五入／切上）を厳密に適用する。共通ロジックは `src/bmcs_app.Domain/Calculations/ConsumptionTaxCalculator.cs`（TODO.md 5-1）に集約する。
   - **端数処理の単位は1円**（`decimal(15,2)` カラムには小数部 `.00` で格納する）。
   - **端数処理の適用単位**は、グループ内の「税種別区分・税率のペア」ごとに1回（税率だけでグループ化すると、税率改定前後で軽減税率と旧標準税率が同じ%になったときに誤って合流するため）。
   - **マイナス金額（返品・値引）は絶対値を丸めて符号を戻す**（切捨＝ゼロ方向に切り捨て、切上＝ゼロから離れる方向に切り上げ、四捨五入＝`MidpointRounding.AwayFromZero`）。これにより同額の返品・値引が元の売上の税額をちょうど打ち消す。
   - **明細金額（数量×単価）にも得意先の端数区分を適用し、1円単位に丸めてから保存する**（数量 `decimal(13,3)` ×単価 `decimal(15,4)` の積は最大7桁の小数になり、丸めずに `decimal(15,2)` カラムへ保存すると SQL Server 側で端数区分を無視した四捨五入が起きるため）。
   - **得意先マスタの端数区分は登録後変更できない**（締め区分・税区分と同じ扱い。2026-09-08 決定）。変更を許すと、発行済み伝票の消費税額を後から再現できず、請求締めで金額が合わなくなるため。
2. **二重集計防止**: 請求の対象は「まだどの請求にも取り込まれていない売上明細行」に限定し、確定時に紐付けを記録して二重計上を防ぐ。**判定は売上明細行単位で行う**（1つの売上伝票の明細行が別々の請求に分かれることがあるため、伝票単位では判定できない）。締め請求と明細請求で紐付けの持ち方が異なる。
   - **締め請求**（締め得意先）: 売上明細行が請求データに取り込まれているかどうかで判定する。取り込み済みの行には請求データへの参照が入る。
   - **明細請求**（都度得意先）: 売上明細行と明細請求書の連携情報が存在するかどうかで判定する。**加えて対象条件を「未請求かつ入金未完了（消込未完了）」に限定し、既に入金済み（消込完了）の売上は未請求であっても明細請求書の対象にしない**。
   - **二重請求はデータベース側でも拒否する。** 1つの売上明細行が紐づける明細請求書は最大1つであり、この制約を一意制約として持たせる。アプリ側の抽出条件だけに依存しない。
   - 締め解除・明細請求書の取消では、紐付けを解除して売上明細行を未請求に戻す。実現方法（カラム／連携テーブル）は [`docs/database-schema.md`](database-schema.md) を参照。
3. **宛名の柔軟性**: 学校・官公庁向けの明細請求では、得意先マスタ自体は変更せず、請求書印字用の宛名だけを都度書き換えられるようにする（C-9・2026-09-10確定。**都度書き換え方式に一本化し、子得意先マスタは作らない**）。
   - ジャーナル系の画面（受注・売上・入金・明細請求書等）は、得意先コードで検索した後、名称欄を手入力で上書き修正できるようにする。これが宛名変更の唯一の手段。
   - 学校－学年－クラスのような階層を持つ得意先も、マスタ上は常に**一つの得意先（1レコード）**として扱う。学年・クラスの違いは親子マスタでは表現せず、伝票入力時の名称上書きだけで表現する。
   - **代表者印字の要否は、宛名（請求先名称）を変更しても、あくまで発行元となる得意先マスタ側の`print_representative_flag`設定に従う**（宛名を変えても代表者印字設定は変わらない）。
4. **入金消込**: 締め得意先は請求単位で古い順に自動消込、都度得意先は伝票・請求書単位でのピンポイント消込。振込手数料差額（`fee_adjustment_amount`）は**手入力とし、自動計算・自動補正提案は行わない**（M-14・2026-09-10確定。手入力のため、しきい値等の自動判定ロジックは不要）。
   - **締め得意先の入金入力画面では、充当先（どの請求にいくら充てたか）は画面に表示しない。** 利用者にとって重要なのは充当先ではなく残高であるため（2026-09-15ユーザー確認）。充当は保存時に内部で自動計算し`receipt_allocation`テーブルに保持する（`docs/database-schema.md` 2.10-1節）。画面には得意先の請求残高のみを表示する。
   - **消込の対象額（TODO.md 7-1・2026-09-14確定）**: 売上明細行の `amount` をそのまま使う。請求単位・伝票単位（外税）は税抜金額、内税明細単位は税込金額（`amount` が既に税込）であり、消費税分は明細行レベルの消込には載せない（例: 明細6,000円＋4,000円＝請求10,000円に対し消費税込11,000円を入金しても、消込の対象は10,000円で税額1,000円分は行に載らない）。
   - **振込手数料差額は消込済金額に含める。** 売上明細行へ反映する消込額 = `allocated_amount + fee_adjustment_amount`。入金9,780円＋手数料差額220円で請求10,000円が消込完了になる。入金側の充当状態（軸「未充当／一部充当／充当完了」）の判定には手数料差額を含めない（実際に受け取った金額の消化状況を表すため）。
   - **締め入金（`receipt`）は請求データ（`billing`）へ充当するが、消込キャッシュ列は売上明細行にある。** billingへ充当した額を、そのbillingに紐づく売上明細行（`billing_number`一致）へ伝票日付→伝票番号→行番号の古い順に配分する。全額充当できる場合は返品・値引行を含む全行がそのまま消込完了になり、不足する場合は正負が一致する行にだけ古い順に配分する（入金がゼロの場合に返品行だけが消込完了になることはない）。
   - **都度得意先の明細入金は、直接指定（売上明細行を名指し）を先に確定し、残額を明細請求書経由の配分に回す。** 1つの売上明細行が両方から充当されうるため、名指しした指示を導出（請求書単位の配分）より優先する。
5. **編集ロック（訂正・取消の方式）**: 訂正・取消は**元伝票の直接修正**とし、赤伝（マイナス伝票）方式は採用しない（C-6・2026-09-10確定）。`sales`（売上）は、次の4条件のいずれかに該当する場合のみ編集不可、それ以外は上書き可能。
   1. **請求締め**: 対象行が確定済み`billing`に集計済み
   2. **明細請求書発行済み**: 都度得意先の対象行が`detail_invoice_sales_line`に連携済み（Phase 6-5・2026-09-14確定。当初「ロック条件に含めない」としていたが、発行済みの明細請求書ヘッダー（確定金額のスナップショット）が実データと乖離する不具合が見つかったため追加した。`docs/design_document.md` 13章）
   3. **月次締め**: 得意先ごとに確定した年月の`monthly_closing`が存在する
   4. **入金済み**: 消込完了
   - （ユーザーによる直接編集が対象。締め処理自身による状態カラム更新は対象外）。解除は管理者権限のみ。**請求締め（`billing`。得意先の締め日単位で集計）と月次締め（`monthly_closing`。全得意先を暦月単位で集計）は別々の締め処理として併存する**（`docs/database-schema.md` 1章・2026-09-09決定）。
   - `order_slip`（受注）はこの4条件のいずれにも該当しないため常に直接修正可能。
   - **`receipt`（締め入金）・`detail_receipt`（明細入金）は`sales`と同じ4条件をそのまま適用しない**（Phase 7-5・2026-09-15確定）。入金は保存直後にほぼ必ず充当完了になるため、条件④（充当完了）をそのまま適用すると訂正・取消できる入金がほぼ存在しなくなり、Phase 7-5の目的自体が成立しない。`detail_receipt`は「月次締め」のみ、`receipt`は「月次締め」に加え「請求締めスナップショット」（伝票日付が確定済み`billing`の集計期間に含まれるかどうか。締め処理が`receipt`の合計額を`billing`へ焼き込んで以後再計算しないため）を独自のロック条件とする。締め解除（6-2）してから訂正・取消する。詳細は`docs/database-schema.md` 1章・`docs/design_document.md` 19章。
   - **締め解除・月次締め解除は、権限差が出る操作のため、それぞれ請求締め・月次締め本体とは別画面（別メニュー項目）として提供する**（C-8・2026-09-10確定。画面内アクション単位の権限判定は行わず、通常のメニュー単位の権限レベル判定だけで制御する）。
6. **受注の引当数量**: 在庫・発注連携は今回のスコープ外だが、引当数量カラムは将来の在庫連携に備えて残す。現時点では自動更新ロジックを持たなくてよい。
7. **商品コード**: 商品コードはJANコードを想定しない。社内商品コードとして扱う。
8. **認証方式**: ログインID/パスワード入力によるログイン画面は設けない。デスクトップ上の起動用ショートカットに実行時パラメータとして社員コードを渡し、アプリ起動時にその社員コードから権限を判定する方式とする。したがってメインメニューにログインUIは不要。
9. **インボイス制度対応**: 適格請求書（インボイス）制度に対応する。請求書・明細請求書は適格請求書の記載事項を満たすものとし、以下を扱う。
   - **記載事項**: 発行者の名称＋適格請求書発行事業者の登録番号／取引年月日／取引内容（軽減税率対象品目には「※」等を付記）／**税率ごとに区分して合計した対価の額と適用税率**／**税率ごとに区分した消費税額**／交付を受ける者の名称。発行者側の情報（登録番号・自社名・住所・代表者名）は自社情報マスタで管理する。
   - **税率の決定**: 商品マスタが税種別区分（標準税率／軽減税率／非課税）を持ち、伝票登録時に税率マスタ（`docs/database-schema.md` 2.3節）から該当する税率を引いて、売上明細行へ税率と税種別区分を**転記（スナップショット）**する。以後マスタ側の税率・区分が変わっても、既存伝票の税計算には影響しない。
   - **税率別内訳の算出**: 請求書に印字する税率別内訳は、対象となる売上明細行を税率ごとにグループ化して集計する。ただし請求データ側にも確定時点の税率別内訳（税率ごとの対価の額・消費税額）を**確定値として保持**し、請求書を再発行しても同じ金額を再現できるようにする。請求データはすでに売上金額・消費税額を確定値として保持しているため、内訳の粒度をそれに揃える趣旨。
   - **端数処理**: 適格請求書における「税率ごとに区分した消費税額」は、**1枚の請求書につき税率ごとに1回**の端数処理を行うのが原則であり、明細ごとに端数処理した税額を積み上げる方法は認められない。得意先マスタの端数区分（切捨／四捨五入／切上）はこの「税率ごと1回」の端数処理に適用する。
   - **【要確認】** 上記の端数処理原則を自然に満たすのは税区分「請求単位」のみであり、「伝票単位」「内税明細単位」は伝票単位・明細単位で端数処理を行うため原則と衝突する。どの書類を適格請求書として扱うか（納品書・明細請求書を適格請求書とするか、請求書側で税率ごとに再計算するか）を含め、顧問税理士および石山商店への確認が必要。詳細は [`docs/design_document.md`](design_document.md) の不明点を参照。
   - **【暫定・C-4b】** 上記が確認・決定するまでは、TODO.md の暫定決定 C-4b に従い**得意先マスタの税区分どおりに端数処理する**（請求単位＝請求ごとに税率ごと1回、伝票単位＝伝票ごとに税率ごと1回、内税明細単位＝明細行ごとに1回）。将来の差し替えを見据えた抽象化は行わない。方針が確定して変更が必要になった場合は `src/bmcs_app.Domain/Calculations/ConsumptionTaxCalculator.cs` と `tests/bmcs_app.Domain.Tests/Calculations/` を直接修正する。
10. **返品・値引（M-9・2026-09-10確定）**: マイナス数量・マイナス金額の伝票とし、`sales.slip_type`（1=売上／2=返品／3=値引）で識別する。
    - **伝票区分は明細行ごとに選択する。** 同一伝票内に売上行と値引行が混在できる（`slip_type` は `slip_date` 等と異なり伝票単位の値ではない）。
    - **値引行も商品コードは必須**（値引専用の擬似商品コードは作らない）。税率・税種別区分がその商品から決まる。
    - **値引の原価は常に0**（現品の移動を伴わないため）。返品は商品原価をそのまま使う（返品時も原価をマイナス計上することで、元の売上の粗利影響をちょうど打ち消す）。正規化ロジックは `src/bmcs_app.Domain/Calculations/SalesSlipTypeRules.cs` に集約する。
    - **返品・値引行を受注に紐付けることはできない。** 受注の売上化済数量を減算するのは売上行のみであり、受注由来の売上を返品したい場合は元の売上行を直接訂正する（共通業務ルール5）。


## 伝票の状態遷移

各伝票の状態は、**互いに独立した複数の軸**として保持する。単一の「ステータス」カラムに複数軸を押し込むことはしない（状態の組み合わせが爆発し、一方の状態を戻したときに他方の情報が失われるため）。

状態の保持方針:

- **絞り込み条件として頻出する状態はカラムとして保持**し、関連伝票の登録・取消・訂正と同一トランザクション内で更新する。
- **それ以外は導出**する。特に月次締め・請求締めによる編集ロックは、伝票側にフラグを持たず、`customer_code`＋伝票日付の年月と`monthly_closing`データの突き合わせ、または`billing`への集計済みかどうかで判定する（締め・解除のたびに大量の伝票行を更新せずに済む）。

### 受注（受注明細行単位）

| 状態 | 意味 |
|---|---|
| 未売上 | 初期状態。売上化されていない |
| 一部売上 | 受注数量の一部が売上化された（分納） |
| 売上完了 | 受注数量のすべてが売上化された |
| 中止 | 失注・キャンセル。売上化しないことが確定 |

遷移: `未売上` →（売上化）→ `一部売上` →（残数量の売上化）→ `売上完了` ／ `未売上`・`一部売上` →（中止操作）→ `中止` ／ `売上完了`・`一部売上` →（売上の取消）→ `一部売上`・`未売上`（逆遷移あり）

- 判定は「受注数量」と「売上化済数量」の比較で行い、売上化済数量もカラムとして保持する。
- **引当は状態に含めない。** 引当数量カラムは将来の在庫連携用に保持するのみで、自動更新ロジックを持たないため（共通業務ルール6）。
- 受注全体（伝票単位）が完了かどうかは、明細行の状態から導出する。
- **中止は伝票単位の操作。**（TODO.md 4-4決定）明細行単位では中止しない。業務上の失注・キャンセルは伝票丸ごとが通常のため。
- **中止は終端状態であり、解除しない。** 上記の遷移図に中止からの逆遷移が無いのはそのため。誤って中止した場合は新規に受注を入力し直す運用とする。

### 売上（売上明細行単位・3軸を独立に保持）

**軸1: 納品書発行状態**

| 状態 | 意味 |
|---|---|
| 未発行 | 納品書を発行していない。データ検索画面の一括発行対象になる |
| 発行済 | 発行日時を保持。再発行は可能で、その場合は発行日時を更新し発行回数を加算する |

**軸2: 請求状態**

| 状態 | 意味 |
|---|---|
| 未請求 | どの請求データ・明細請求書にも取り込まれていない |
| 請求済 | 締め得意先は請求データに取り込まれた／都度得意先は明細請求書に紐付いた |

- 締め請求と明細請求で紐付けの実現方法は異なるが（詳細は `docs/database-schema.md`）、業務ルールとしての状態は共通。
- 逆遷移: 締め解除・明細請求書の取消により `請求済` → `未請求` に戻す。

**軸3: 消込状態**

| 状態 | 意味 |
|---|---|
| 未消込 | 入金が充当されていない |
| 一部消込 | 一部が充当された |
| 消込完了 | 全額が充当された |

- 消込済金額をカラムで保持し、売上金額との比較で状態を決める。
- **消込済金額はキャッシュ列であり、入金データ（`receipt`／`detail_receipt`）から都度再計算して確定する（手入力しない）。** 売上金額を超えて消し込まれることはなく、超過分（過入金）は入金側に残る（TODO.md 7-1・`docs/design_document.md` 16章）。

**明細請求書の対象条件**（共通業務ルール2の再掲）: 軸2 = `未請求` かつ 軸3 ≠ `消込完了`。

### 入金（入金明細行単位）

| 状態 | 意味 |
|---|---|
| 未充当 | どの売上にも充当されていない |
| 一部充当 | 入金額の一部を売上に充当した（充当残あり＝前受・過入金） |
| 充当完了 | 入金額の全額を充当した |

- **充当状態はキャッシュ列であり、同一伝票（`receipt_slip_number`／`detail_receipt_number`）の全行の `allocated_amount` 合計と、伝票単位の値である入金額（`receipt_amount`）との比較で判定する（TODO.md 7-1）。振込手数料差額（`fee_adjustment_amount`）は含めない。**

### 請求データ（締め請求）

| 状態 | 意味 |
|---|---|
| 確定 | 請求締め処理で確定した。請求書発行の対象 |
| 解除済 | 締め解除された。集計・残高計算の対象外。再締めでは新しいレコードを作る |

- 締め解除時に物理削除はしない。一度発行した請求書を追跡できるようにするため、確定日時・確定者・解除日時・解除者を保持する。

### 明細請求書

| 状態 | 意味 |
|---|---|
| 発行済 | 初期状態（発行時にレコードが作られる） |
| 取消 | 取消済。取消時に売上明細行との紐付けを解除し、売上側の請求状態を `未請求` に戻す |

### 月次締め

**得意先×暦月末日で1レコード**（`billing`の締め期間とは別に、全得意先を暦月で集計する。`docs/database-schema.md` 1章・2.16節）。

| 状態 | 意味 |
|---|---|
| 未締め | 該当得意先・該当年月のレコードが存在しない状態 |
| 確定 | 確定済。該当得意先の該当年月の伝票日付を持つ売上・入金は編集不可（共通業務ルール5） |
| 解除済 | 管理者権限で解除された。編集可能に戻る（`billing`と同じ非破壊方式。物理削除しない） |

### 取消・訂正の操作方法（C-6・2026-09-10確定、2026-09-15 Phase 7-5で`receipt`／`detail_receipt`の条件を確定）

取消・訂正は**元伝票の直接修正**で行う（赤伝方式は採用しない）。`sales`が修正不可になるのは、共通業務ルール5の4条件（請求締め・明細請求書発行済み・月次締め・入金済み）のいずれかに該当する場合のみで、それ以外は自由に直接修正できる。上記の逆遷移（`請求済`→`未請求`、`消込完了`→`一部消込` 等）は、対象行が4条件に該当しない限り、直接修正によって自然に生じる（専用の「取消」操作を都度呼ぶ必要はない）。`order_slip`（受注）はいずれの条件にも該当しないため、状態にかかわらず常に直接修正可能。

`receipt`（締め入金）・`detail_receipt`（明細入金）は`sales`と条件が異なる。`detail_receipt`は月次締めのみ、`receipt`は月次締めに加え「請求締めスナップショット」（伝票日付が確定済み`billing`の集計期間に含まれるか）に該当する場合のみ修正不可（共通業務ルール5参照）。画面（入金入力・明細入金）は、伝票No.欄で既存伝票を読み込んだ後、そのまま編集して保存＝訂正、取消操作＝取消として扱う（得意先の付け替えのみ常に不可）。
