# Product Spec

ドメイン仕様・業務フローの詳細。
このファイルは業務仕様（用語・業務フロー・UI/UX・共通業務ルール・伝票の状態遷移）の正である。プロジェクト構成・技術は architecture.md、DB は database-schema.md、帳票は report-spec.md、画面は design_document.md を正とする。


## 用語

| 用語 | 意味 |
|---|---|
| 締め得意先 | 20日締め・末日締めなど決まった締め日で1か月分の売上をまとめて請求する得意先。売上入力時点では請求書を発行しない |
| 都度得意先 | 官公庁・学校など、締め処理を行わず売上1件〜数件ごとに明細請求書を発行する得意先 |
| 税単位（`tax_unit`） | 消費税の計算単位。1＝請求単位、2＝伝票単位、3＝内税明細単位。得意先マスタの税区分で決まり、登録後は変わらない |
| 受注 | 仮伝票。入荷・引当完了後に売上化する。請求・消込の対象外 |
| 売上 | 納品の実績を表す伝票（明細行単位で請求・消込の状態を持つ）。返品・値引もマイナスの売上として扱う |
| 請求締め（締め請求） | 締め得意先の未請求の売上明細行を集計して請求データ（`billings`）を確定し、月次請求書を発行する処理 |
| 請求データ（`billings`） | 請求締めで確定する集計値のヘッダー。税率別内訳を確定値で保持する |
| 明細請求書 | 都度得意先向けに、売上明細行を選んで都度発行する請求書（`detail_invoices`） |
| 入金（締め入金） | 締め得意先の入金。請求データへ古い順に自動で充当する（`receipts`／`receipt_allocations`） |
| 明細入金 | 都度得意先の入金。売上明細行または明細請求書を名指しして消込む（`detail_receipts`） |
| 充当 | 入金額を請求または売上明細行へ割り当てること |
| 消込 | 売上明細行の請求額に対して入金額を充てた結果。未消込／一部消込／消込完了の状態を持つ |
| 振込手数料差額 | 入金額と請求額の差のうち手数料として扱う額。手入力で、消込済金額に含める |
| 元帳（得意先元帳） | 得意先ごとの売上・入金を時系列に並べ、残高推移を示す帳票・画面。残高の正 |
| 月次締め | 全得意先を暦月単位で集計・確定する処理（`monthly_closings`）。確定した月の伝票は編集できない |
| 編集ロック | 請求締め・明細請求書発行済み・月次締め・消込完了のいずれかに該当する売上を訂正・取消できなくすること。伝票側にフラグは持たず導出する |
| 締め解除 | 確定した請求締めを解除済みにし、売上を未請求に戻す処理。管理者のみ |
| 月次締め解除 | 確定した月次締めを解除済みにする処理。管理者のみ |
| 請求集約先／請求集約元 | 他の得意先の分もまとめて請求される得意先／請求が他の得意先に集約される得意先（「親得意先」「子得意先」とは呼ばない） |
| 宛名 | 請求書の印字用の名称。得意先マスタは変えず、伝票入力時に名称欄を上書きして指定する |
| 適格請求書 | インボイス制度に対応した請求書。請求書・明細請求書が対象で、納品書は含めない |
| 税種別区分 | 標準税率／軽減税率／非課税の区分。伝票登録時に税率とともに売上明細行へ転記する |
| 伝票区分（`slip_type`） | 売上／返品／値引。明細行ごとに選ぶ |
| 権限レベル | 社員マスタの数値。メニューごとの必要レベル以上の社員にだけそのメニューを表示する（9＝管理者専用、1＝一般） |


## UI/UX
MahApps.Metro と既存スタイルへ合わせる。
派手さより可読性・誤操作防止・状態の明確さを優先する。

特に:
- 画面操作全般は、マウスだけでなくキーボードでの操作を前提に設計する（マウスでしか完結しない操作を作らない）
- 日付は `YYYY/MM/DD` 表記で統一
- 金額・数量はカンマ区切り・右揃え、入力はカンマなし数値でblur時に自動整形
- `Tab` だけでなく `Enter` でも次項目へフォーカス移動（誤送信させない）
- 検索モーダル・明細一覧は上下矢印キーで行選択、`Enter` で確定・転記
- フォーカス中の入力欄は背景色を変えて視認性を上げる
- プリンタ設定はDB管理せず、`bmcs_config.json`（実行ファイルと同じフォルダ）へ端末ごとに保存する
- **起動直後のフォーカス**: 画面表示直後は、伝票番号／マスタコードの入力欄にカーソルがある状態にする（例: 売上入力→売上No、入金入力→入金No、得意先マスタ保守→得意先コード）。伝票番号・コードを持たない画面（請求締め処理等）は、画面内で一番最初の入力フィールドにフォーカスを置く。
- **ジャーナル系画面の伝票No入力欄の挙動**（売上入力・受注入力・明細請求書発行・入金入力等、伝票Noを持つ画面共通）:
  - 空欄のまま `Enter`: 新規登録モードとして、伝票No欄の次の入力欄（売上入力→売上日付、受注入力→受注日付、明細請求書発行→請求日付）へカーソル移動する。入力済みのデータは消さない。
  - 伝票Noを入力して `Enter`: その伝票No の伝票を呼び出し、空欄時と同じ「伝票No欄の次の入力欄」へカーソル移動する。ただし読込後に画面全体が読み取り専用表示になる画面（明細請求書発行の既存分読込等）は、移動先の入力欄が存在しないため伝票No欄にカーソルを留める。
  - 入力された伝票Noが存在しない場合はエラーを表示する（新規登録モードへは進まない。入力済みの得意先・明細等も破棄しない）。
  - `Space` キー押下で伝票検索ダイアログを表示する。
  - 対象は売上入力・受注入力・明細請求書発行・入金入力の4画面。請求締め処理・締め解除処理は請求Noを扱うが新規登録モードの概念が無く対象外。
- **登録後のリセット**: 保存・登録処理が成功した後は「登録しました」的な完了メッセージを表示し、画面を起動直後の状態（新規入力可能な空の状態）に戻して、先頭項目へ自動でフォーカスを戻す。
- **リスト選択の確定操作**: 検索モーダル・明細一覧など、一覧からの選択操作は `Enter` キーによる確定を基本としつつ、ダブルクリックでも同じ動作（同じコマンド）を呼び出す。


## 共通業務ルール

1. **消費税・端数処理**: 得意先マスタの税区分（請求単位／伝票単位／内税明細単位）と端数区分（切捨／四捨五入／切上）を厳密に適用する。共通ロジックは `src/bmcs_app.Domain/Calculations/ConsumptionTaxCalculator.cs` に集約する。
   - **端数処理の単位は1円**（`decimal(15,2)` カラムには小数部 `.00` で格納する）。
   - **端数処理の適用単位**は、グループ内の「税種別区分・税率のペア」ごとに1回（税率だけでグループ化すると、税率改定前後で軽減税率と旧標準税率が同じ%になったときに誤って合流するため）。
   - **マイナス金額（返品・値引）は絶対値を丸めて符号を戻す**（切捨＝ゼロ方向に切り捨て、切上＝ゼロから離れる方向に切り上げ、四捨五入＝`MidpointRounding.AwayFromZero`）。これにより同額の返品・値引が元の売上の税額をちょうど打ち消す。
   - **明細金額（数量×単価）にも得意先の端数区分を適用し、1円単位に丸めてから保存する**（数量 `decimal(13,3)` ×単価 `decimal(15,4)` の積は最大7桁の小数になり、丸めずに `decimal(15,2)` カラムへ保存すると SQL Server 側で端数区分を無視した四捨五入が起きるため）。
   - **得意先マスタの端数区分は登録後変更できない**（締め区分・税区分と同じ扱い）。変更を許すと、発行済み伝票の消費税額を後から再現できず、請求締めで金額が合わなくなるため。
2. **二重集計防止**: 請求の対象は「まだどの請求にも取り込まれていない売上明細行」に限定し、確定時に紐付けを記録して二重計上を防ぐ。**判定は売上明細行単位で行う**（1つの売上伝票の明細行が別々の請求に分かれることがあるため、伝票単位では判定できない）。締め請求と明細請求で紐付けの持ち方が異なる。
   - **締め請求**（締め得意先）: 売上明細行が請求データに取り込まれているかどうかで判定する。取り込み済みの行には請求データへの参照が入る。
   - **明細請求**（都度得意先）: 売上明細行と明細請求書の連携情報が存在するかどうかで判定する。**加えて対象条件を「未請求かつ入金未完了（消込未完了）」に限定し、既に入金済み（消込完了）の売上は未請求であっても明細請求書の対象にしない**。
   - **二重請求はデータベース側でも拒否する。** 1つの売上明細行が紐づける明細請求書は最大1つであり、この制約を一意制約として持たせる。アプリ側の抽出条件だけに依存しない。
   - 締め解除・明細請求書の取消では、紐付けを解除して売上明細行を未請求に戻す。実現方法（カラム／連携テーブル）は [`docs/database-schema.md`](database-schema.md) を参照。
3. **宛名の柔軟性**: 学校・官公庁向けの明細請求では、得意先マスタ自体は変更せず、請求書印字用の宛名だけを都度書き換えられるようにする（**都度書き換え方式に一本化し、子得意先マスタは作らない**）。
   - ジャーナル系の画面（受注・売上・入金・明細請求書等）は、得意先コードで検索した後、名称欄を手入力で上書き修正できるようにする。これが宛名変更の唯一の手段。
   - 学校－学年－クラスのような階層を持つ得意先も、マスタ上は常に**一つの得意先（1レコード）**として扱う。学年・クラスの違いは親子マスタでは表現せず、伝票入力時の名称上書きだけで表現する。
   - **代表者印字の要否は、宛名（請求先名称）を変更しても、あくまで発行元となる得意先マスタ側の`print_representative_flag`設定に従う**（宛名を変えても代表者印字設定は変わらない）。
   - この宛名の都度書き換えは、後述の「親子請求（請求集約）」とは別の話である。
4. **入金消込**: 締め得意先は請求単位で古い順に自動消込、都度得意先は伝票・請求書単位でのピンポイント消込。振込手数料差額（`fee_adjustment_amount`）は**手入力とし、自動計算・自動補正提案は行わない**（手入力のため、しきい値等の自動判定ロジックは不要）。
   - **入金方法（現金・振込・手形・相殺等）は`deposit_methods`マスタで管理し、利用者が自由に追加・編集できる**（`docs/design_document.md` 27章・`docs/database-schema.md` 2.6-1節）。
   - **締め得意先の入金入力画面では、充当先（どの請求にいくら充てたか）は画面に表示しない。** 利用者にとって重要なのは充当先ではなく残高であるため。充当は保存時に内部で自動計算し`receipt_allocations`テーブルに保持する（`docs/database-schema.md` 2.10-1節）。画面には得意先の請求残高のみを表示する。
   - **消込の対象額**: 売上明細行の `amount` をそのまま使う。請求単位・伝票単位（外税）は税抜金額、内税明細単位は税込金額（`amount` が既に税込）であり、消費税分は明細行レベルの消込には載せない（例: 明細6,000円＋4,000円＝請求10,000円に対し消費税込11,000円を入金しても、消込の対象は10,000円で税額1,000円分は行に載らない）。
   - **振込手数料差額は消込済金額に含める。** 売上明細行へ反映する消込額 = `allocated_amount + fee_adjustment_amount`。入金9,780円＋手数料差額220円で請求10,000円が消込完了になる。入金側の充当状態（軸「未充当／一部充当／充当完了」）の判定には手数料差額を含めない（実際に受け取った金額の消化状況を表すため）。
   - **締め入金（`receipts`）は請求データ（`billings`）へ充当するが、消込キャッシュ列は売上明細行にある。** billingへ充当した額を、そのbillingに紐づく売上明細行（`billing_number`一致）へ伝票日付→伝票番号→行番号の古い順に配分する。全額充当できる場合は返品・値引行を含む全行がそのまま消込完了になり、不足する場合は正負が一致する行にだけ古い順に配分する（入金がゼロの場合に返品行だけが消込完了になることはない）。
   - **都度得意先の明細入金は、直接指定（売上明細行を名指し）を先に確定し、残額を明細請求書経由の配分に回す。** 1つの売上明細行が両方から充当されうるため、名指しした指示を導出（請求書単位の配分）より優先する。
5. **編集ロック（訂正・取消の方式）**: 訂正・取消は**元伝票の直接修正**とし、赤伝（マイナス伝票）方式は採用しない。`sales`（売上）は、次の4条件のいずれかに該当する場合のみ編集不可、それ以外は上書き可能。
   1. **請求締め**: 対象行が確定済み`billings`に集計済み
   2. **明細請求書発行済み**: 都度得意先の対象行が`detail_invoice_sales_lines`に連携済み（都度得意先の`billing_number`は常にNULLで請求締めの条件が働かず、発行済みの明細請求書ヘッダー（確定金額のスナップショット）が実データと乖離するため。`docs/design_document.md` 13章）
   3. **月次締め**: 得意先ごとに確定した年月の`monthly_closings`が存在する
   4. **入金済み**: 消込完了
   - （ユーザーによる直接編集が対象。締め処理自身による状態カラム更新は対象外）。解除は管理者権限のみ。**請求締め（`billings`。得意先の締め日単位で集計）と月次締め（`monthly_closings`。全得意先を暦月単位で集計）は別々の締め処理として併存する**（`docs/database-schema.md` 1章）。
   - `orders`（受注）はこの4条件の対象外（受注は請求・消込の対象外）だが、**未売上（`order_status`＝未売上）の伝票のみ直接修正可能**。一部売上・売上完了・中止済みの伝票は読み込めるが修正できない。中止（伝票単位）は一部売上でも可能なのに対し、修正は未売上限定という非対称があるが、意図した仕様（`OrderEditLockEvaluator`）。
   - **`receipts`（締め入金）・`detail_receipts`（明細入金）は`sales`と同じ4条件をそのまま適用しない。** 入金は保存直後にほぼ必ず充当完了になるため、条件④（充当完了）をそのまま適用すると訂正・取消できる入金がほぼ存在しなくなり、入金の訂正・取消という機能自体が成立しない。`detail_receipts`は「月次締め」のみ、`receipts`は「月次締め」に加え「請求締めスナップショット」（伝票日付が確定済み`billings`の集計期間に含まれるかどうか。締め処理が`receipts`の合計額を`billings`へ焼き込んで以後再計算しないため）を独自のロック条件とする。締め解除してから訂正・取消する。詳細は`docs/database-schema.md` 1章・`docs/design_document.md` 19章。
   - **締め解除・月次締め解除は、権限差が出る操作のため、それぞれ請求締め・月次締め本体とは別画面（別メニュー項目）として提供する**（画面内アクション単位の権限判定は行わず、通常のメニュー単位の権限レベル判定だけで制御する）。
   - 対象行が上記の条件に該当しない限り、逆遷移（`請求済`→`未請求`、`消込完了`→`一部消込` 等）は直接修正によって自然に生じる（専用の「取消」操作を都度呼ぶ必要はない）。
   - 画面（入金入力・明細入金）は、伝票No.欄で既存伝票を読み込んだ後、そのまま編集して保存＝訂正、取消操作＝取消として扱う（得意先の付け替えのみ常に不可）。
6. **受注の引当数量**: 在庫・発注連携は今回のスコープ外だが、引当数量カラムは将来の在庫連携に備えて残す。現時点では自動更新ロジックを持たなくてよい。引当は受注の状態に含めない（自動更新ロジックを持たないため）。
7. **商品コード**: 商品コードはJANコードを想定しない。社内商品コードとして扱う。
8. **認証方式**: ログインID/パスワード入力によるログイン画面は設けない。デスクトップ上の起動用ショートカットに実行時パラメータとして社員コードを渡し、アプリ起動時にその社員コードから権限を判定する方式とする。したがってメインメニューにログインUIは不要。
9. **インボイス制度対応**: 適格請求書（インボイス）制度に対応する。請求書・明細請求書は適格請求書の記載事項を満たすものとし、以下を扱う。
   - **記載事項**: 発行者の名称＋適格請求書発行事業者の登録番号／取引年月日／取引内容（軽減税率対象品目には「※」等を付記）／**税率ごとに区分して合計した対価の額と適用税率**／**税率ごとに区分した消費税額**／交付を受ける者の名称。発行者側の情報（登録番号・自社名・住所・代表者名）は自社情報マスタで管理する。
   - **税率の決定**: 商品マスタが税種別区分（標準税率／軽減税率／非課税）を持ち、伝票登録時に税率マスタ（`docs/database-schema.md` 2.3節）から該当する税率を引いて、売上明細行へ税率と税種別区分を**転記（スナップショット）**する。以後マスタ側の税率・区分が変わっても、既存伝票の税計算には影響しない。
   - **税率別内訳の算出**: 請求書に印字する税率別内訳は、対象となる売上明細行を税率ごとにグループ化して集計する。ただし請求データ側にも確定時点の税率別内訳（税率ごとの対価の額・消費税額）を**確定値として保持**し、請求書を再発行しても同じ金額を再現できるようにする。請求データはすでに売上金額・消費税額を確定値として保持しているため、内訳の粒度をそれに揃える趣旨。
   - **端数処理**: 適格請求書における「税率ごとに区分した消費税額」は、**1枚の請求書につき税率ごとに1回**の端数処理を行うのが原則であり、明細ごとに端数処理した税額を積み上げる方法は認められない。得意先マスタの端数区分（切捨／四捨五入／切上）はこの「税率ごと1回」の端数処理に適用する。
   - **【要確認】** 上記の端数処理原則と税区分（「伝票単位」「内税明細単位」）の整合、およびどの書類を適格請求書として扱うかが未確定（顧問税理士および石山商店への確認が必要）。詳細は [`docs/design_document.md`](design_document.md) の不明点を参照。
   - **端数処理の現行方針**: 上記が確認・決定するまでは**得意先マスタの税区分どおりに端数処理する**（請求単位＝請求ごとに税率ごと1回、伝票単位＝伝票ごとに税率ごと1回、内税明細単位＝明細行ごとに1回）。将来の差し替えを見据えた抽象化は行わない。方針が確定して変更が必要になった場合は `src/bmcs_app.Domain/Calculations/ConsumptionTaxCalculator.cs` と `tests/bmcs_app.Domain.Tests/Calculations/` を直接修正する。
10. **返品・値引**: マイナス数量・マイナス金額の伝票とし、`sales.slip_type`（1=売上／2=返品／3=値引）で識別する。
    - **伝票区分は明細行ごとに選択する。** 同一伝票内に売上行と値引行が混在できる（`slip_type` は `slip_date` 等と異なり伝票単位の値ではない）。
    - **値引行も商品コードは必須**（値引専用の擬似商品コードは作らない）。税率・税種別区分がその商品から決まる。
    - **値引の原価は常に0**（現品の移動を伴わないため）。返品は商品原価をそのまま使う（返品時も原価をマイナス計上することで、元の売上の粗利影響をちょうど打ち消す）。正規化ロジックは `src/bmcs_app.Domain/Calculations/SalesSlipTypeRules.cs` に集約する。
    - **返品・値引行を受注に紐付けることはできない。** 受注の売上化済数量を減算するのは売上行のみであり、受注由来の売上を返品したい場合は元の売上行を直接訂正する（共通業務ルール5）。

## 親子請求（請求集約）

複数の締め得意先の売上を、1つの得意先の請求書にまとめて計上する仕組み。どの得意先の売上をどの得意先の請求書として計上するかを表す正式なマスタ構造（`billing_customer_code`）であり、宛名の都度書き換え（共通業務ルール3。得意先マスタは1レコードのまま変わらない）とは別の話である。両者を区別するため、請求集約側では「子得意先」という語を使わず、売上を集約される側を**請求集約元**、請求書を作る側を**請求集約先**と呼ぶ。

- **請求データ（`billings`）は請求集約先にしか作らない。** 請求集約元の売上明細行も締め対象抽出の範囲に含め、請求集約先の請求番号を書き込む。
- **入金は請求集約先にしか入らない。** 請求集約元の得意先コードを入金入力画面で指定すると業務例外で拒否する。売掛残高の管理も請求集約先に集約し、請求集約元では残高を管理しない。
- **得意先元帳は、請求集約元を開いたときは残高・繰越を表示せず、取引履歴（売上）のみを表示する**（残高が常に未回収のように見えてしまうため）。

詳細は`docs/database-schema.md` 1-1節・`docs/design_document.md` 28章。

## 伝票の状態遷移

各伝票の状態は、**互いに独立した複数の軸**として保持する。単一の「ステータス」カラムに複数軸を押し込むことはしない（状態の組み合わせが爆発し、一方の状態を戻したときに他方の情報が失われるため）。

状態の保持方針:

- **絞り込み条件として頻出する状態はカラムとして保持**し、関連伝票の登録・取消・訂正と同一トランザクション内で更新する。
- **それ以外は導出**する。特に月次締め・請求締めによる編集ロックは、伝票側にフラグを持たず、`customer_code`＋伝票日付の年月と`monthly_closings`データの突き合わせ、または`billings`への集計済みかどうかで判定する（締め・解除のたびに大量の伝票行を更新せずに済む）。

### 受注（受注明細行単位）

| 状態 | 意味 |
|---|---|
| 未売上 | 初期状態。売上化されていない |
| 一部売上 | 受注数量の一部が売上化された（分納） |
| 売上完了 | 受注数量のすべてが売上化された |
| 中止 | 失注・キャンセル。売上化しないことが確定 |

遷移: `未売上` →（売上化）→ `一部売上` →（残数量の売上化）→ `売上完了` ／ `未売上`・`一部売上` →（中止操作）→ `中止` ／ `売上完了`・`一部売上` →（売上の取消）→ `一部売上`・`未売上`（逆遷移あり）

- 判定は「受注数量」と「売上化済数量」の比較で行い、売上化済数量もカラムとして保持する。
- 受注全体（伝票単位）が完了かどうかは、明細行の状態から導出する。
- **中止は伝票単位の操作。** 明細行単位では中止しない。業務上の失注・キャンセルは伝票丸ごとが通常のため。
- **中止は終端状態であり、解除しない。** 上記の遷移図に中止からの逆遷移が無いのはそのため。誤って中止した場合は新規に受注を入力し直す運用とする。

### 売上（売上明細行単位・3軸を独立に保持）

**軸1: 納品書発行状態**

| 状態 | 意味 |
|---|---|
| 未発行 | 納品書を発行していない。データ横断検索画面の一括発行対象になる |
| 発行済 | 発行日時を保持。再発行は可能で、その場合は発行日時を更新し発行回数を加算する |

**軸2: 請求状態**

| 状態 | 意味 |
|---|---|
| 未請求 | どの請求データ・明細請求書にも取り込まれていない |
| 請求済 | 締め得意先は請求データに取り込まれた／都度得意先は明細請求書に紐付いた |

- 締め請求と明細請求で紐付けの実現方法は異なるが（詳細は `docs/database-schema.md`）、業務ルールとしての状態は共通。
- 逆遷移: 締め解除・明細請求書の取消により `請求済` → `未請求` に戻す。

**軸3: 消込状態**

| 状態 | 意味 |
|---|---|
| 未消込 | 入金が充当されていない |
| 一部消込 | 一部が充当された |
| 消込完了 | 全額が充当された |

- 消込済金額をカラムで保持し、売上金額との比較で状態を決める。
- **消込済金額はキャッシュ列であり、入金データ（`receipts`／`detail_receipts`）から都度再計算して確定する（手入力しない）。** 売上金額を超えて消し込まれることはなく、超過分（過入金）は入金側に残る（`docs/design_document.md` 16章）。

### 入金（入金明細行単位）

| 状態 | 意味 |
|---|---|
| 未充当 | どの売上にも充当されていない |
| 一部充当 | 入金額の一部を売上に充当した（充当残あり＝前受・過入金） |
| 充当完了 | 入金額の全額を充当した |

- **充当状態はキャッシュ列であり、同一伝票（`receipt_slip_number`／`detail_receipt_number`）の全行の `allocated_amount` 合計と、伝票単位の値である入金額（`receipt_amount`）との比較で判定する。** 振込手数料差額（`fee_adjustment_amount`）は含めない（共通業務ルール4）。

### 請求データ（締め請求）

| 状態 | 意味 |
|---|---|
| 確定 | 請求締め処理で確定した。請求書発行の対象 |
| 解除済 | 締め解除された。集計・残高計算の対象外。再締めでは新しいレコードを作る |

- 締め解除時に物理削除はしない。一度発行した請求書を追跡できるようにするため、確定日時・確定者・解除日時・解除者を保持する。

### 明細請求書

| 状態 | 意味 |
|---|---|
| 発行済 | 初期状態（発行時にレコードが作られる） |
| 取消 | 取消済。取消時に売上明細行との紐付けを解除し、売上側の請求状態を `未請求` に戻す |

### 月次締め

**得意先×暦月末日で1レコード**（`billings`の締め期間とは別に、全得意先を暦月で集計する。`docs/database-schema.md` 1章・2.16節）。

| 状態 | 意味 |
|---|---|
| 未締め | 該当得意先・該当年月のレコードが存在しない状態 |
| 確定 | 確定済。該当得意先の該当年月の伝票日付を持つ売上・入金は編集不可（共通業務ルール5） |
| 解除済 | 管理者権限で解除された。編集可能に戻る（`billings`と同じ非破壊方式。物理削除しない） |
