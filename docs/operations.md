# bmcs_app 運用

運用担当向け。構築は `docs/setup.md`、配布は `docs/release.md`、スキーマ変更の運用は `docs/database-schema.md` 3.2節を参照。

---

## 1. ログ

| 項目 | 内容 |
|---|---|
| 場所 | 各端末の `%LOCALAPPDATA%\bmcs_app\logs\log-YYYYMMDD.txt`（端末ごと。DBには保存しない） |
| 保持 | 日次ローリング、直近31ファイル |
| 書式 | `yyyy/MM/dd HH:mm:ss.fff [レベル] ソース メッセージ` ＋例外 |
| レベル | `appsettings.json` の `Serilog:MinimumLevel`（既定 Information。`Microsoft` と `Microsoft.EntityFrameworkCore` は Warning） |

- UIスレッドの未処理例外は Error として記録し、「処理中にエラーが発生しました」のダイアログ（ログの場所つき）を表示する。アプリは継続する。
- UIスレッド外の未処理例外は Fatal として記録する。
- 障害の問い合わせでは、**発生した端末の当日のログ**を回収する。

## 2. 主なエラーと対処

### 2.1. 他のユーザーが更新しました（rowversion 競合）

「他のユーザーが同じ売上・入金を更新しました。再読み込みしてください。」等のメッセージが出る。同じ伝票・マスタを別の端末が先に更新した状態。

- 自動マージ・後勝ち上書きはしない。**再読み込みして内容を確認し、入力し直す。**
- 訂正モードで保存に失敗した画面は、再読み込みするまで保存できない。
- 頻発する場合は、同じ伝票を複数人が同時に開く運用になっていないかを確認する。

### 2.2. 伝票番号

- 採番は `slip_number_sequences`（系列: `order_slip`／`sales_slip`／`receipt_slip`／`detail_receipt`／`billing`／`detail_invoice`）で、伝票の保存と同じトランザクション内で行う。保存に失敗すれば採番も戻るため、通常は欠番にならない。
- 8桁ゼロ埋め、年次リセットなし。8桁を超えると桁数が増え、文字列としての並び順が崩れる。
- 系列の初期行が無いと採番は例外になる。系列の追加は新しい連番SQLで INSERT する。
- 番号を手作業で書き換えない。伝票番号＋行番号が主キーのため重複はDBが拒否する。

### 2.3. 起動できない

| 症状 | 原因と対処 |
|---|---|
| `接続文字列 'BmcsDb' が設定されていません` | `appsettings.Development.json` が無い、または空。配布先の設定を確認する（`docs/release.md`） |
| 起動時に「起動に失敗しました」 | ログを確認。DB接続不可（サーバ停止・ネットワーク・認証）が多い |
| メインメニューが空 | 起動引数の社員コードが社員マスタに無い、または権限が足りない（`menus.required_permission_level` ≦ 社員の権限レベルのメニューだけ出る） |

### 2.4. 印刷・PDF

- プリンタ設定は端末ごとの `bmcs_config.json`（`docs/release.md`）。未設定または指定プリンタが無い場合は印刷ダイアログに切り替わる。
- PDF保存は Windows の「Microsoft Print to PDF」を使う。この機能が無効だと保存できない。

## 3. データ補正の原則

- **業務データは画面から訂正・取消する。** 訂正は元伝票の直接修正で、編集ロック（請求締め・明細請求書発行済み・月次締め・消込完了）に該当する伝票は、先にロックの原因（締め解除など）を解消する。
- 伝票は物理削除しない（取消は `is_deleted`）。
- **消込のキャッシュ列（`sales.settled_amount`／`settlement_status` 等）の再計算は `SettlementService` のみが行う。** SQL で直接書き換えない。ずれが疑われる場合は、画面操作（対象の入金・売上の訂正保存など）で `SettlementService` を経由させる。
- どうしても SQL で補正する場合は、事前にバックアップを取り、`bmcs_db` を明示し、トランザクション内で件数を確認してからコミットする。補正内容は記録を残す。
- 画面から直せない状態（締め済みの誤り）は 4章の手順で解除してから訂正する。

---

## 4. 誤確定時の締め解除（業務手順）

解除の画面は管理者権限（権限レベル9）のみ。解除は、対象が「最新の確定」であることが条件。

### 4.1. 請求締めの誤確定

1. **請求締め解除**画面で、解除したい請求日を指定して内容を確認する。
2. 実行すると、その請求日の確定済みの請求データがすべて解除済みになり、売上の請求済み状態が未請求に戻る。**一括処理で、1件でも解除できないものがあれば何も更新しない。**
3. 解除できるのは、得意先ごとに最新の確定請求のみ。後続の締めがある場合は、後の締めから順に解除する。
4. 解除後、売上を訂正して、請求締め処理をやり直す。
5. 入金の充当先（`receipt_allocations`）は付け替えられない。解除後に消込は再計算される。

### 4.2. 月次締めの誤確定

1. **月次締め解除**画面で、解除する集計年月を指定する。
2. 指定した年月の確定済み行がすべて解除済みになる。後続の年月が確定済みの得意先がある場合は解除できない（後の月から順に解除する）。
3. 解除後、編集ロックは即時に外れる。訂正して、月次締め処理をやり直す（再確定は解除済みの行を上書きする）。

### 4.3. 明細請求書の誤発行

明細請求書の取消は、入金の充当先になっていないものだけ可能。取消後、売上は再び請求候補に現れる。

## 5. 期首・年度運用

- 年度の切り替え処理は無い。伝票番号は年次リセットせず通し番号で採番する。
- 月次締めは暦月単位。月次締めの前月残高は前月の確定行の当月残高から引き継ぐ。
- 締め済みの月への売上・入金の新規登録は拒否される。
