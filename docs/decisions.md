## アーキテクチャ・層構成

- **Presentation から Infrastructure への参照禁止はコンパイラで強制せず、コードレビューで担保する**: .NET SDK の `ProjectReference` は推移的に伝播するため、`bmcs_app` の csproj が Infrastructure を参照しなくても Application 経由で型が見える。強制手段は3案とも失敗した。①`DisableTransitiveProjectReferences=true` はコンパイル参照を遮断できるが `bmcs_app.Infrastructure.dll` が出力ディレクトリにコピーされず実行時に読み込めない。②①に `ExcludeAssets="compile"` 付きの明示参照を加えると dll はコピーされるがコンパイル参照も復活して遮断できない。③`ReferenceOutputAssembly="false"` ＋手動コピーは実現できるが MSBuild の細工が過剰。機械的に守らせたくなった場合は MSBuild ではなく、参照関係を検査するアーキテクチャテストを追加する。理由: 要確認（採用理由の記録なし）。
- **下位3層（Domain / Application / Infrastructure）の TFM に `-windows` を付けない（`net10.0`）**: WPF の型が下位層に混入することをコンパイラで防ぐため。推移参照の影響を受けないので確実に効く。WPF 層のみ `net10.0-windows`。
- **.NET 10 を採用する**: LTS であり、.NET 9 は 2026年5月にサポート終了済みのため。
- **帳票のレンダリング・印刷・PDF出力・プレビューは Presentation 層（`src/bmcs_app/Reports/`）に置く**: 帳票方式が WPF の `FixedDocument`/`FixedPage`/`PrintQueue` に依存し、Infrastructure（`net10.0`、WPF なし）には置けない。Infrastructure を `net10.0-windows`＋`UseWPF` にすると、参照元の Application と単体・結合テストの2プロジェクトまで推移的に WPF 依存になるため採らない。データ取得は業務領域フォルダ（例: `Application/Sales/`）の Application サービスが担い、WPF 型を含まないプレーンな DTO（値は decimal/DateOnly のまま持ち、書式は付けない）を返す。Application 層の機能フォルダは `Order/Sales/Billing/Receipt/Ledger/Closing/Master/Search/Common` に限定されており、納品書データの取得は `sales` テーブルを読む売上の責務のため `Application/Reports/` ではなく `Application/Sales/` へ置く。
- **機能別にプロジェクトを分けず、フォルダで分ける**: 十数画面という規模に対して参照管理とビルド時間の負担が見合わないため。機能ごとに exe を分けても得られるのは「別プロセスで動く」ことだけで、同じ exe の多重起動と等価なので分けない。
- **リポジトリのインターフェースを作らず、Application が `DbContext` を直接使う。Domain エンティティを EF Core の POCO として兼用し DTO へ詰め替えない**: 差し替えを見据えた抽象化を行わない方針のため。
- **起動時のスキーマ検証をしない**: 起動が遅くなるため。コードと DB の乖離は、変更作業と同一作業内で SQLCMD により DB を追従させ、疑われる場合は `sys.columns`/`sys.tables` を照会してエンティティ定義と突き合わせて確認する。
- **DbContext はウィンドウ単位でスコープを分ける（`WindowService` が `IServiceScopeFactory` でウィンドウごとにスコープを作り、`Window.Closed` で破棄する）**: 単一の `DbContext` を全ウィンドウで共有すると、受注画面の未保存の変更が売上画面の保存時に一緒に書き込まれるため。ウィンドウ生成は必ず `WindowService.Show<TWindow, TViewModel>()` 経由にし、`new` で直接生成しない。
- **`WindowService.Show` の `configure` コールバックは値の設定のみ行い、非同期の初期化処理をしない**: `Show` は `window.Show()` の前に `configure` を呼ぶが、View の `Loaded`（→ ViewModel の `LoadCommand`）はその後に非同期で発火する。`configure` 側で非同期処理（DB 読込等）をすると実行順が保証されない。読込は各 `LoadAsync` の末尾で、`configure` が設定した値（例: `PreviewSlipNumber`）を見て行う。
- **帳票プレビューは `ShowDialog`（モーダル）で開く（複数画面の並行利用の例外）**: ①プレビューは印刷前の確認作業であり長時間開けたままにする文書ではない、②印刷成功→発行記録（`DeliveryNoteService.MarkIssuedAsync` 等）の順序をコールバックなしで保証できる、の2点から、他画面を操作できなくなることを許容する。
- **`DbContext` の並行利用（`Task.WhenAll` 等）をしない**: `DbContext` はスレッドセーフではない。並行させたい場合はスコープ（＝ `DbContext`）を分ける。
- **共通検索モーダル（得意先・商品・伝票）はマスタ／対象を全件ロードしてメモリ内で絞り込む**: 既存の得意先・商品マスタ画面の全件ロード方針に揃えたもの。マスタが数万件規模になった場合は、性能問題が出てから両方まとめてサーバ側絞り込みに変更する。

## トランザクション・採番・非同期

- **`TransactionScope` を使わない**: `Database.CurrentTransaction` は `TransactionScope` 配下では `null` のままになり、`SlipNumberService.NextAsync` の「明示トランザクション未開始なら `InvalidOperationException`」ガードが常に発火するため。
- **`EnableRetryOnFailure`（EF Core の自動リトライ）を使わない**: ユーザー起動トランザクション（`BeginTransactionAsync`）は再試行戦略と併用できないため、有効化すると採番が全面的に失敗する。
- **伝票番号の採番は伝票登録と同一トランザクション内で行い、別 Tx で先にコミットしない**: 登録が失敗したときに欠番が出る（業務上説明が難しい）ため。採番テーブルの行ロックがトランザクション終了まで残るが、同時利用者は数十人規模で実用上問題にならない。呼び出し順は「メモリ上でグラフ構築 → `BeginTransactionAsync` → `NextAsync` → 番号を明細行へ代入 → `SaveChangesAsync`（1回） → `CommitAsync`」。画面を開いた時点や入力開始時に採番しない（ロックがコミットまで残るため、UI 操作をまたいで Tx を開けない）。
- **同一トランザクション内で複数の採番系列（`SlipNumberKind`）を取る場合は、列挙値の宣言順で取得する**: 取得順が呼び出し元ごとに異なると ABBA デッドロックの可能性があるため。
- **`SlipNumberService.NextAsync` は明示トランザクション未開始なら `InvalidOperationException` を投げる**: 採番だけが暗黙トランザクションで先にコミットされる事故を実行時に確実に検出するためのアサーション（抽象化ではない）。
- **`SqlQuery<T>` で `UPDATE ... OUTPUT` を実行する場合は必ず `ToListAsync()` で受ける**: `FirstOrDefaultAsync`/`SingleAsync`/`Take(1)` 等を使うと LINQ 合成と判定され、EF が生SQLを派生テーブルに包み、SQL Server が実行時エラーを返す（コンパイルは通るため気付きにくい）。LINQ を後付けしないスカラークエリなら生SQLがそのまま1コマンドとして発行される。実装例は `SlipNumberSequenceCommand.IncrementAsync`。
- **生SQL・ストアドの呼び出しは Infrastructure 層に置く**: Application 層に生SQLが散らばらないようにするため。ストアド化の目安は「1回の処理で 1,000 行超の更新・集計」で、それ未満は LINQ。超えてもまず LINQ で書いて実測し、遅い場合のみストアド化する。推測でストアドを選ばない。
- **`ConfigureAwait(false)` を付けない**: `.Result`/`.Wait()`/`.GetAwaiter().GetResult()` を禁止しているためデッドロックは起きず、付けても効果はわずかな性能差にとどまり、全 `await` に付ける手間と読みにくさに見合わない。付ける／付けないの混在が最も問題なので、統一して付けない。
- **Application 層の非同期メソッドは `CancellationToken cancellationToken = default` を既定シグネチャにする**: 既定値で呼ぶだけなら追加コストがなく、将来キャンセル導線を追加するときにシグネチャ変更が要らないため。実際にキャンセルさせるのは当面、長時間処理（請求締め・月次締め・帳票の一括発行）に限る（単票の登録・参照は実装量に対して得るものが小さい）。
- **`SaveChangesAsync` を1ユースケース内で2回呼ぶ場合は明示トランザクションで包む（入金消込の再計算、入金訂正の充当再構築）**: 再計算方式は毎回 DB 上の確定値から全件導出するため、入力を保存した後でなければ再計算の入力が揃わない。入金訂正では `GetOutstandingBillingsAsync` がサーバー側の `GroupBy`/`ToDictionaryAsync` クエリで ChangeTracker 上の未コミット論理削除を見ないため、旧充当を論理削除して一度 `SaveChangesAsync` してから再取得しないと、自分自身の旧充当が「まだ生きている」とカウントされ、未消込残額が実際より少なく計算される（全額充当済みの請求へ減額訂正すると全額が前受行 `billing_number = NULL` に落ちる）。このため `receipts` の訂正は全面再構築（`receipt_allocations` を全論理削除→途中で `SaveChangesAsync` を1回→残高を再取得→再配分）とし、`receipts` 本体は行単位の差分で更新する。`SettlementService`／`OrderStatusService.ApplySalesQuantityDeltasAsync` は自身で Tx を開始せず、呼び出し元の明示トランザクションに参加し、未開始なら `InvalidOperationException` を投げる。
- **保存失敗後の ChangeTracker 汚染に対し、①既存行コピー時（`ApplyLineValues`）に `IsDeleted = false` を明示設定し、②訂正モード中の保存が例外で失敗したら ViewModel が `IsReloadRequired` を立てて再読込まで保存を封じる**: `DbContext` はウィンドウ単位スコープで画面を開いている間生き続けるため、`UpdateAsync` がミューテーション後に例外を投げると ChangeTracker が汚れたまま残る。同じ画面から再保存すると、EF のアイデンティティ解決で以前の `IsDeleted = true` のインスタンスが返り黙って論理削除される、または前回 `Add` した新規行が残り同一キーの `InvalidOperationException` になる。`OrderEntryViewModel`／`SalesEntryViewModel` の両方に適用（`CanSave` に `!IsReloadRequired` を含める）。
- **競合検出時は自動マージ・後勝ち上書きをしない**: 金額が静かに壊れることを避けるため（画面に「他のユーザーが更新しました。再読み込みしてください」を表示）。`DbUpdateConcurrencyException` は Application 層で業務的な結果に変換し、ViewModel に EF Core の例外型を漏らさない。

## EF Core マッピング

- **FK は、ナビゲーションプロパティを持たなくても `HasOne<TPrincipal>().WithMany().HasForeignKey(...)` で全件登録する**: 省略すると、複数エンティティを同一 `SaveChangesAsync()` で保存したときに EF Core が依存関係を解決できず、INSERT の順序が（観測した限り）テーブル名のアルファベット順になり、FK 制約違反を起こす。理由: 要確認（採用理由の記録なし）。
- **ナビゲーションプロパティを持たせない**: 得意先元帳はアプリ側 LINQ で複数テーブルをマージする方針で、`Include()` によるナビゲーション経由の結合を使わないため。使わない抽象化を先回りして作らない。
- **`decimal` は `HasPrecision(p, s)` を必ず明示する**: 省略すると既定精度（18,2）になり、`decimal(15,4)` の単価カラム等で桁落ちする。
- **`varchar`/`char` 列は `.IsUnicode(false)` を必ず明示する**: 省略すると EF Core が `nvarchar` パラメータを送り、SQL Server 側で暗黙変換が発生してインデックスを使えなくなる。コード系カラムは PK/FK で全 JOIN に絡むため実害が大きい。
- **`ToTable()` でテーブル名を必ず明示する**: 省略すると DbSet プロパティ名からの命名変換に暗黙に追従してしまう。DDL を正とし、DbSet 名の変更でテーブル名が意図せず連動しないようにするため。
- **PascalCase ↔ snake_case は `EFCore.NamingConventions`（`UseSnakeCaseNamingConvention()`）に任せ、数字を含む列名（`address1`/`address2` 等）も含めて `HasColumnName` は書かない**: 列名の対応を1か所（命名規約）に集約するため。
- **`date` 型は C# `DateOnly` にマッピングする**: EF Core 8+ のネイティブ対応で、時刻成分を持たせないことでバグを防ぐ。
- **監査列は共通基底クラス（`TrackedEntity` → `AuditableEntity`）と共通拡張メソッドで重複排除する。税単位別の共通基底クラス／拡張は持たない**: `sales`/`receipts`/`billings` は統合済みで派生クラスがなく、共有すべき基底が存在しないため。

## UI・入力・キーボード操作

- **フォーカス移動は ViewModel 起点の `RequestFocus(string focusKey)`（`FocusRequested` イベント＋ `FocusBehavior` の `FocusKey` 添付プロパティ）に統一し、`EnterKeyNavigationBehavior` 自体は変更しない**: 「Enter に対する `KeyBinding` を持つ TextBox では譲る」ガードへ `CanExecute` 判定を足す案は、`[RelayCommand]` 生成の `AsyncRelayCommand` が既定で実行中に `CanExecute()` を false にするため、非同期 Lookup 実行中に Enter を二度押すとフォーカスが勝手に飛ぶ誤爆が起き、しかもこのビヘイビアは多数の画面に適用済みで無関係な欄（得意先コード欄・商品コード欄など）まで波及するため却下した。明示キー指定にするのは、XAML の宣言順が「日付→伝票No」のため `MoveFocus(FocusNavigationDirection.Next)` では日付欄に戻れないため。なお `EnterKeyNavigationBehavior` は `PreviewKeyDown`（トンネリング）で動くため、`TextBox.InputBindings` に一致する `Enter` の `KeyBinding` を持つ要素ではフォーカス移動をスキップする（さもないと子の `KeyBinding` より先にイベントを消費し、商品コード欄の「Enter でコード確定」等が機能しない）。この結果、プレビュー中（`IsReadOnly` のみで `KeyBinding` は残る）の伝票No欄では Enter で次項目へ移動しない（Tab は機能する）。
- **`KeyBinding` は `IsEnabled=false`／`IsReadOnly` でも生きるため、コマンドの `CanExecute`（`CanEdit => !IsPreviewMode` を合成）とコマンド本体先頭の `if (IsPreviewMode) return;` の二重で防御する**: `Space`/`Return` の `KeyBinding` は XAML の `IsReadOnly`/`IsEnabled` バインドだけでは塞げない。取消系コマンド（`DeleteSlipAsync`）は `CanExecute` の合成漏れがあると、未消込・未締めの伝票をプレビュー中に本当に取消してしまうため。受注の訂正モードでも同様に、得意先コード欄を `IsReadOnly` にするだけでは Space/Return のキーバインド経由で得意先が差し替わるため、検索・コード照会の2コマンドも `CanExecute` で無効化する。
- **プレビュー（読み取り専用）時の明細行グリッドは `IsEnabled="{Binding IsEditable}"` で `ItemsControl` ごと無効化する**: 行単位の読み取り専用フラグでは区分コンボ・×削除ボタン・商品検索の `InputBindings` をまとめて無効化できないため。トレードオフとして明細行全体が灰色になる（見やすさより「編集できない」を機械的に保証することを優先）。`ScrollViewer` 自体を無効化するとスクロールできなくなるため、`IsEnabled` は内側の `ItemsControl` に付ける。
- **`WindowTransitionsEnabled="False"` を各 `MetroWindow` のルート要素に個別に付ける**: `CommonControlStyles.xaml` の `MetroWindow` 暗黙スタイル（`BasedOn` 有無いずれも）で一括設定を試みたが、実機で実効値が常に既定の `True` のままで効かなかった（原因は MahApps.Metro 内部実装と推測されるが特定できていない）。XAML 属性のローカル値は WPF のプロパティ値優先順位で最上位のため、スタイル解決に依存せず確実に効く。画面追加時は必ず付ける。理由: 要確認（採用理由の記録なし）。
- **日付を保持する ViewModel プロパティは `DateTime?`（時刻成分は必ず `00:00:00`）で持ち、`string` や `DateOnly?` にしない**: 標準 `DatePicker`（全画面デザイン統一）の `SelectedDate` が `DateTime?` のため、直接バインドできる型に合わせる。`string` 保持は採らない: `DateOnly` に既定の `TypeConverter` がなく `TextBox.Text` との双方向バインディングが失敗するためで、`DatePicker.SelectedDate` へ直接バインドできる `DateTime?` ならこの問題は起きない。
- **`DatePickerInputBehavior` を暗黙 `DatePicker` スタイルで全画面一律適用する（他のビヘイビアと異なりオプトインにしない）**: 8桁ベタ打ち（`20260101`）の入力速度を維持するため、内部 `PART_TextBox` の入力を Enter 確定／フォーカス離脱時に `yyyy/MM/dd` へ正規化し、解釈できない入力は直前の `SelectedDate` へ巻き戻す。`DatePicker` は日付専用で誤爆せず、キー操作の意味を変える `EnterKeyNavigationBehavior`／`RowActivationBehavior` と異なり書式整形（`FormattedTextBoxBehavior` と同種）であり、XAML への書き忘れをなくす利点を優先した。`EnterKeyNavigationBehavior`／`RowActivationBehavior`／`FormattedTextBoxBehavior` はダイアログ等への意図しない波及を避けるためオプトイン。
- **`FrameworkElement.Language` を `App.xaml.cs` の `OnStartup` で `ja-JP` に固定する**: `DatePicker` は `Language` 由来のカルチャで表示書式（`ShortDatePattern`）を決めるため、設定しないと `9/15/2026` 表記になり「日付は `yyyy/MM/dd` で統一」が崩れる。
- **`DatePicker` の読み取り専用は `mah:ControlsHelper.IsReadOnly` で表し、`IsEnabled` を使わない**: `DatePicker` に `IsReadOnly` プロパティが無い。`IsEnabled` はグレーアウトしタブ順から外れ、読み取り専用でもフォーカス・コピー可能という現状の挙動が変わるため。
- **`TextBox`/`ComboBox`/`DatePicker` の暗黙スタイルに共通の `MinHeight`（`Styles/Metrics.xaml` の `InputControlHeight`、実測で確定）と `VerticalAlignment="Center"`・`VerticalContentAlignment="Center"` を設定して入力欄の高さを統一する（`Button` は `MinHeight` のみ、`VerticalAlignment=Center` は付けない）**: MahApps 既定では `ComboBox` の自然高が `TextBox` より大きく、`RowDefinition` 未指定の `Grid`（子が `Stretch`）に混在させると行高が `ComboBox` に引っ張られ、画面ごとに高さがバラつく。`VerticalAlignment=Center` で各コントロールを行高から独立させ、`MinHeight` を3種の自然高の最大値以上に取ることで一致させる。
- **画面上の数量・金額は小数点以下を表示しない（`DecimalPlaces` 既定0、`N0`、`MidpointRounding.AwayFromZero`）が、帳票の単価のみ `N4`（小数4桁）を維持する**: 単価の内部精度（`decimal(15,4)` 等）は保持し画面表示のみ丸める。画面の単価欄はマスタ入力用の丸め表示、帳票の単価は明細金額の根拠を示す表示、という役割の違いによる（ユーザー判断で単価は据え置き）。帳票の数量は画面と同じく `N0`。
- **ViewModel は WPF の `Brush` 等の Media 型を持たず、整数インデックス（`ColorIndex`）だけを持ち、View 側の Converter で Brush へ変換する**: ViewModel を WPF 依存にしないため（`EnumDisplayConverter` と同じ方針）。

## 税・端数

- **端数処理の適用単位は「税種別区分×税率」のペアごとに1回**: 税率だけでグループ化すると、税率改定前後で軽減税率と旧標準税率が同じ%になったときに誤って合流するため。
- **マイナス金額（返品・値引）は絶対値を丸めて符号を戻す**（切捨＝ゼロ方向、切上＝ゼロから離れる方向、四捨五入＝`MidpointRounding.AwayFromZero`）: 同額の返品・値引が元の売上の税額をちょうど打ち消す（符号対称）ため。例: 切上の得意先で-1100×8÷108=-81.4815…は-82.00になり、元売上の税額と打ち消し合う。
- **明細金額（数量×単価）も得意先の端数区分で1円単位に丸めてから保存する**: 数量`decimal(13,3)`×単価`decimal(15,4)`の積は最大7桁の小数になり、丸めずに`decimal(15,2)`カラムへ渡すと、SQL Server側が端数区分を無視した四捨五入をしてしまうため。`tax_amount`／`slip_tax_amount`も1円単位（小数部は常に`.00`）で確定する。
- **端数区分（`rounding_type`）は登録後変更不可**（締め区分・税区分と同じ扱い。マスタ画面は新規登録時のみ入力可）: 変更を許すと発行済み伝票の消費税額を後から再現できず、請求締めで金額が合わなくなるため。伝票単位の請求締めでの税額再計算検証や、明細請求書発行時の税額一致検証も「端数区分は不変だから一致するはず」を前提にしており、不一致はデータ異常として例外にする。請求集約の先／元で端数区分が食い違うと、この検証が締め当日に失敗してグループ全体の請求書が発行できなくなるため、集約する得意先どうしも端数区分を一致させる（変更不可なので、端数区分が異なる既存の2得意先は集約関係にできず、どちらかの得意先コードを取り直す必要がある）。
- **税率・税種別区分は売上明細行・受注明細行に転記（スナップショット）する**: 伝票時点の税率を行内に持つことで、マスタ側の税率改定が既存伝票に影響しないようにするため（非正規化方針と同趣旨）。税率別内訳の集計はこのカラムでグループ化する。税種別区分の識別子・カラム名に具体的な税率（%）を書かない（税率改定で名称が実態と食い違うため。税率は施行日付きの税率マスタで解決する）。非課税は税率マスタを参照せず税率0を転記する。
- **請求データ（`billings`）・明細請求書に税率別内訳を固定カラムの確定値で保持する**（標準税率／軽減税率の対価額・税額、非課税の対価額）: 請求書を再発行しても金額が変わらないようにするため。子テーブルにしないのは、日本の税種別区分が少数の閉じた集合であり、「請求データは集計値のみのヘッダー1テーブル」という方針を崩さずに済むため。請求書の明細部分は売上ジャーナルから都度組み立てるが、税額は確定値を印字する。
- **商品マスタは外税単価と内税単価を別カラムで持つ**: 得意先の`tax_unit`により同一得意先への販売は常に外税か内税のどちらか一方に固定される（混在しない）ため、売上・受注の`unit_price`には得意先の`tax_unit`から一意に決まる側（`tax_unit=3`は内税単価、1・2は外税単価）を転記する。内税/外税の別は商品側の属性ではない。非課税品は税の内外の区別がないため、両単価に同じ値を設定する運用とする。
- **締め得意先＝外税（請求単位・伝票単位）、都度得意先＝内税（内税明細単位）に限定し、締め区分と税区分を独立入力させない**（`税区分＝内税明細単位 ⇔ closing_day=0`をCHECK制約＋アプリ側バリデーションで強制。残りの組み合わせ〔内税×請求単位／内税×伝票単位／外税×明細単位〕は業務上発生しないので扱わない）: 独立に入力できると次の2パターンで破綻する。(1) 締め得意先＋内税明細単位: 明細単位バケットには前月繰越残高を持つ請求データが存在せず、請求締め処理が実行できない。(2) 都度得意先＋請求単位: 請求締め時に消費税を一括計算する前提のため、締めを行わない都度得意先では消費税の確定タイミングが決まらない。この組み合わせに限定される根拠はインボイス制度上のもの。「登録後変更不可」は運用中にバケットが移る問題を解消するだけで、登録時にどの組み合わせを許すかの問題は閉じない。最初の1回の登録を間違えられないため、制約の必要性はむしろ高い。
- **得意先の締め区分（`closing_day`の0／非0）と税区分は登録後変更不可**: 変更すると既存の売上・入金・請求データの`tax_unit`と食い違い整合が取れなくなるため。移行処理は実装しない。DB側でも、`customers`の`UNIQUE(customer_code, tax_unit)`を`sales`／`receipts`／`billings`から複合FKで参照しており、伝票が1件でもある得意先の`tax_unit`をUPDATEするとFK違反（Msg 547）で拒否される（直接SQLへの最後の防波堤）。
- **端数処理は暫定として得意先マスタの税区分どおりに行い、差し替えを見据えた抽象化はしない**（請求単位＝請求ごとに税率ごと1回／伝票単位＝伝票ごとに税率ごと1回／内税明細単位＝明細行ごとに1回）: 適格請求書の「税率ごとの消費税額」は1枚の請求書につき税率ごとに1回の端数処理が原則で、明細ごとに丸めた税額の積み上げは認められないが、これを自然に満たすのは請求単位のみであり、伝票単位・内税明細単位は原則と衝突する。どの書類を適格請求書とするか、伝票単位の請求書で伝票ごとの確定税額合計を印字してよいか、明細請求書で明細ごと税額の合計を印字してよいか、が顧問税理士確認待ちのため。再検討条件: 確定して変更が必要になれば`ConsumptionTaxCalculator`とそのテストを直接修正する。
- **請求書・明細請求書の税率別内訳は「金額＝ヘッダーの確定値、税率(%)ラベル＝該当する税種別区分を持つ明細行から借りる」方式で組み立てる**（`ConsumptionTaxCalculator.ResolveConfirmedBuckets`）: `billings`／`detail_invoices`は税種別区分ごとの確定金額しか持たず税率(%)を持たないが、適用税率は適格請求書の法定記載事項であり印字が必要。一方、明細行を税率ごとに再グループ化して丸め直すと、伝票単位（伝票ごとに端数処理する構造）ではヘッダー確定値と金額が食い違う（二重丸め）ため。対価額・税額とも0の区分は表示せず、明細0件（締め解除済み・取消済み）で該当区分が無いときは税率0でフォールバックする。
- **納品書は適格請求書として扱わない**（「本書は適格請求書です」等の文言は印字しない）: 適格請求書の記載事項の対象として挙げているのは請求書・明細請求書のみで、納品書を含めていないため。ただしこれは税理士確認待ちの「どの書類を適格請求書とするか」を閉じる決定ではない。再検討条件: 確認結果が変われば`DeliveryNoteDocumentBuilder`の注記追加だけを直接修正する。登録番号・自社名・軽減税率「※」注記は、適格請求書か否かに関わらず有用なため税単位を問わず印字する（税率別内訳は請求単位以外で印字する）。自社情報未登録時は、登録番号が欠落した紙を出さないため印刷を中止する。
- **納品書フッターは税単位で変える**: 請求単位は伝票時点で税額を持たない（CHECK制約でNULL強制）ため税抜合計のみ＋「消費税は月次請求書にてご確認ください」を表示し、仮計算の税額は印字しない（月次請求書側で税率ごとに1回丸め直すため、印字すると請求書と食い違う事故になる）。伝票単位は税率別内訳＋保存済み`slip_tax_amount`（全行同値なのでSUMしない。再計算した内訳合計が保存値と食い違えばログ警告して丸め規約の退行を検知）。内税明細単位は保存済み`tax_amount`を行ごとに合算して内訳・消費税合計を作る（再計算しない。端数区分変更後の伝票でDBと食い違うため）。内税明細単位の単価・金額列は「(税込)」表記にする。

## 締め・請求・月次

- **二重集計の判定は売上明細行単位で行い、二重請求はDBの一意制約でも拒否する**: 1つの売上伝票の各明細行が別々の請求（明細請求書）に分かれることがあり、伝票単位では判定できないため。締め請求は`sales.billing_number`、明細請求は`detail_invoice_sales_lines`の有無で判定する。連携テーブルは`UNIQUE(sales_slip_number, sales_line_number)`を持ち、「多対多」は伝票レベルの話で明細行レベルでは1行が紐づく明細請求書は最大1つ。アプリの抽出条件だけに依存しない。
- **請求締め（`billings`、得意先ごとの締め日期間）と月次締め（`monthly_closings`、全得意先を暦月）は別の締め処理として併存させる**: 集計期間が一致しないため。20日締めの得意先は`billings`が1/21〜2/20、`monthly_closings`が2/1〜2/28を集計する。2/21〜2/28分は当該得意先自身の次回請求締め（3/20）を通っておらず、`tax_unit=1`は伝票時点で税額を確定しないため、この区間の税額は月次締め確定処理が`ConsumptionTaxCalculator`を確定させずに呼んで仮計算する。都度得意先（`tax_unit=3`）も月次締めの対象。
- **月次の仮計算した税額は`sales.slip_tax_amount`に書かず、`monthly_closings`側のカラムにのみ保存する**: `tax_unit=1`は`slip_tax_amount`がNULL固定のCHECK制約`CK_sales_tax_amount_by_tax_unit`に違反するため（書けば制約違反。書けたとしても請求締めでの確定前に税額が固定されてしまう）。
- **請求締め時の売上は集計期間の下限なし、入金は前回確定`billings`の締め日+1日を下限にする（非対称）**: 売上は`billing_number IS NULL`を集計済みマーカーにでき、下限を設けないことで前回締め日より前の日付で後から登録された未請求売上も次回締めで必ず拾える（締め漏れ防止）。入金は`receipt_allocations.billing_number`が「充当先の請求」であり、入金入力が過去の請求へ古い順に充当したときに設定される値なので、締めの「集計済み」マーカーとして上書きできず、期間で区切るしかないため。罠: 前回締め日より前の日付で後から登録された入金はどの締めの期間にも入らず永久に拾われない（対処は締め解除→再締め。既知・許容）。前回確定`billings`が無ければ前回残高0・入金の下限なし。
- **締め解除できるのは同一得意先の確定済み`billings`のうち`closing_year_month`が最新のものだけ**: 古いものを解除すると、より新しい確定済み`billings`が引き継いだ`previous_balance`の参照元が失われ、前回残高チェーンが破綻するため（締め時の「より新しい年月の確定済みがあれば拒否」＝締め順序の逆転防止と対）。解除後は1つ前が最新になるので、古い方へ順に連鎖解除できる。月次締めの解除の順序制約は「締め解除・月次締め解除」節を参照。
- **締め解除は請求日（`billing_date`）指定の一括で、対象に1件でも解除不可があれば全体を中止して何も更新しない（全件成功のみ）**: 請求締めが「締め日を指定して一括」確定するのと粒度を揃えるため。`billing_date`は締め切り日をそのまま書いた値で、締め1回を一意に指すキーになる。一部だけ解除してスキップする扱いはしない。全件成功にする積極的な理由: 要確認（記録なし）。月次締め解除も同じ形（「締め解除・月次締め解除」節）。
- **締め解除では、充当済みの入金（`receipt_allocations`）を付け替えない**: `SettlementService`は入力データ（`allocated_amount`／`fee_adjustment_amount`）を書き換えないため。解除された`billings`を指したままの充当行は残り、解除で外れた売上行の消込キャッシュ列だけを再計算で未消込へ戻す。後にその入金を訂正すると、再構築時の充当先は確定済み`billings`のみが対象になるので、別の確定済み`billings`があればそちらへ、無ければ前受行へ回る（方針の自然な帰結で、新たな防止策は設けない）。付け替えを行わないと決めた積極的な理由: 要確認（記録なし）。
- **請求データ（`billings`）・月次締め（`monthly_closings`）は物理削除せず、状態を「解除済」にする（非破壊）**: 請求は一度発行した請求書を追跡できるようにするため、月次は一度確定した月次残高を追跡できるようにするため。確定・解除の日時と実施者を保持する。再締めでは`billings`は新しい`billing_number`を採番する。
- **二重締め防止は、アプリ側の事前チェックに加えて、確定済みだけを対象にしたフィルタ付き一意インデックス`UQ_billings_customer_closing_ym_confirmed`（`(customer_code, closing_year_month) WHERE billing_status=1 AND is_deleted=0`）をDBに持つ**: 同一得意先・同一締め年月の確定済み請求が2件存在できないことをDBでも強制するため。`billing_status=1`のみが対象なので解除済み（2）は対象外になり、解除→再締めで新番号を採番しても壊れない（非フィルタの一意制約ではこの運用が壊れる）。rowversionだけでは「確定済みの再確定」「解除済みの再解除」といった業務的に不正な遷移は防げないので、状態遷移の前提はアプリ側でも更新前に必ず確認する。
- **`BillingClosingService.ConfirmAsync`はプレビュー結果を引数に取らず、確定時に同条件で再集計する**: プレビューと確定の間に他ユーザーが伝票を登録しても、古い集計値で確定しないため。金額を出す経路（集計メソッド）はプレビューと確定で1本にする。
- **請求締めの対象年月は別入力にしない**: 請求日から導出できる冗長な入力だったため。
- **明細請求書の「未請求」判定は`detail_invoice_sales_lines`に連携行が存在しないことだけを唯一の正とし、`sales.billing_status`は写しとして扱う**: 明細請求は締め請求（`billing_number`）と違い連携テーブルの有無が正で、`billing_status`はその写しに過ぎないため。万一両者が食い違っても、連携行が無い行は候補に出て再請求でき自己修復になる。対象は未請求かつ消込完了でない`tax_unit=3`行。抽出条件は候補表示と発行時の再確認で同じメソッドに1本化する。
- **`detail_invoice_sales_lines`は`row_version`を持たない**: 行の追加・削除しか発生せず更新が無いため。排他制御はトランザクション内での候補条件の再確認とDBの一意制約が担保する（監査列は持つ）。
- **明細請求書の取消は非破壊: ヘッダー`detail_invoices`は物理削除せず`invoice_status`を取消済にして`cancelled_at`／`cancelled_by`を立て、連携行は物理削除して売上行を未請求に戻す**: ヘッダーの確定金額（スナップショット）を取消後も金額追跡用に残すため（締め解除と同じ非破壊方式）。連携行を削除すると「どの明細請求書にも連携していない」という候補条件が自動的に真に戻り、一意制約も解放されるので、同じ売上を新しい明細請求書へ再発行できる。副作用: 取消済み請求書を読み込むと明細は0件でヘッダーの確定金額のみになる（締め解除済みの請求書も同様。印刷の扱いは「帳票」節を参照）。
- **明細請求書の取消は、(1) 連携先の売上明細行に消込済み（一部消込・消込完了）が含まれる場合、(2) この明細請求書を指定した明細入金（`target_type=2`）が存在する場合に拒否する**: (1) 取消して未請求に戻すと、入金済みなのに未請求という業務上あり得ない状態になるため。(2) 取消すると入金の充当先が宙に浮くため。締め解除と異なり明細請求書には繰越残高が無く、どの明細請求書も他の明細請求書の集計に依存しないので、締め順序の制約は無い。
- **`sales.billing_status`と実際の紐付けの一致には、DBのCHECK制約を追加しない**: `tax_unit=3`側は連携テーブルの存在確認が必要でCHECK制約として書けず、`tax_unit`1/2側だけ制約を足しても非対称が残るため。アプリのトランザクションだけが担保する（二重請求・二重締めにはDBの最終防衛線があるのと非対称であることを承知の上での判断）。
- **明細請求書は一覧を持たず、明細請求書No.の直接入力（Enterで既存分を読込、Spaceで検索モーダル）で開く**: 得意先／商品マスタ・締め解除処理と同じコード直接入力方式に統一するため。既存分は読み取り専用（`detail_invoices`は発行済み／取消の2状態で訂正の概念が無く、訂正は取消→再発行で行うため）。検索モーダルは宛名（`addressee_name`）でも検索できる（都度得意先は学校のクラス・先生単位など宛名で識別することが多いため）。取消済みも検索結果に含める。
- **`detail_invoices`は`customer_name`（得意先マスタのスナップショット）と`addressee_name`（請求書に印字する都度入力の宛名）を別カラムで持つ**: 宛名は請求書印字用に都度書き換えるが、発行元の得意先マスタは変更しないため（学校・官公庁向けの宛名の柔軟性を、子得意先マスタではなく名称欄の都度上書きで実現する方針）。宛名は得意先コード確定時に得意先名を初期値として転記し、手入力で上書きする。代表者印字の要否は「帳票」節の代表者の項を参照。
- **都度得意先（`tax_unit=3`）の`sales.billing_number`は常にNULL**: 内税明細単位は締め請求データ（`billings`）を持たず、明細請求書との紐付けは連携テーブルで行うため（`CK_sales_billing_number_by_tax_unit`で強制）。発行時に更新するのは`sales.billing_status`のみ。
- **月次締め（`monthly_closings`）は集計結果を保存し、確定時点の値を以後参照する**: `tax_unit=1`の暦月末時点の税額が、都度計算では確定できないため（`billings`の締め期間と暦月が食い違い、`sales`側に税額を書けない。請求確定前は仮計算のため、確定した行の税額は都度再計算すると異なる値になり得る）。性能が理由ではない。担当者別売上・粗利の集計は保存せず都度集計する（性能問題が出たら別途集計テーブルを追加）。集計キーは伝票の担当者（`sales.employee_code`）。
- **月次締めの消費税額は`当月残高 − 前月残高 − 売上額 + 入金額`で逆算する**: 当月残高＝元帳の月末残高、前月残高＝前月確定行の当月残高（無ければ元帳の月初残高）とすることで、「前月残高＝前月行の当月残高」の連続性を優先しつつ、確定時点で元帳の月末残高と完全に一致させるため。`tax_unit=1`では前月に仮計算した税が請求締め後に確定値へ置き換わり、前月行の当月残高と「今計算し直した元帳の月初残高」が食い違うことがあり、そのずれを消費税額で吸収する。罠: 吸収したずれは税率別内訳に配分しないので、内訳の税額合計が消費税額と一致しないことがある。請求集約元の行は残高式が成り立たず、合計すると売上が請求集約先の行と二重計上されるので、集計に使うときは請求集約元の行を除外する。
- **月次締めで当月の行が解除済みのとき、新しい行を作らず既存行を今回の集計値で上書きして確定に戻す（解除日時・解除者をクリア）**: 主キー（`closing_date`, `customer_code`）が同じで新しい行を作れないため。
- **伝票の状態は軸ごとに独立したカラムで保持し（単一のステータスに集約しない）。編集ロックは状態カラムにせず導出する（「売上の編集ロック」を参照）**: 単一ステータスに複数軸を押し込むと状態の組み合わせが爆発し、一方の状態を戻したときに他方の情報が失われるため。頻出する絞り込み条件はキャッシュ列（関連伝票の登録・取消・訂正と同一トランザクションで更新）にする。

## 入金・消込

### 消込の計算方式・スコープ

- **消込キャッシュ列は、入金データ（`receipts`／`receipt_allocations`／`detail_receipts`）から請求集約グループ（単独得意先なら1得意先）単位で毎回全件再計算する（差分適用はしない）**: 差分方式では、訂正で充当先（`billing_number`等）そのものが変わるケースを追跡しきれずキャッシュがドリフトするため。公開メソッドは`SettlementService.RecalculateForBillingGroupAsync`の1本のみで、得意先の`TaxUnit`により締め向け・都度向けへ内部分岐する。
- **再計算のスコープを「伝票」ではなく「得意先（グループ）」にする**: (1) `customer_code`は`sales`／`receipts`／`detail_receipts`とも伝票単位の値で訂正でも変わらないため、充当先が変わっても変更前後の両グループを自動的に再計算でき、差分追跡が不要になる。(2) 都度得意先の「直接指定」と「明細請求書経由」の合算が、得意先の全売上・全明細入金が同時に視界に入ることで単純なローカル計算になる。(3) 消込整合性レビューが同じ関数を「実態」の定義として再利用できる。
- **再計算は「値が実際に変わった行だけ」をModifiedにする（`TouchAll`は使わない）**: `TouchAll`は編集中の1伝票に対する意図的なrowversion照合強制だが、再計算は得意先の全行に及ぶ派生更新であり、全行を対象にすると無関係な伝票を編集中の別ユーザーを不要に弾くため。真に競合すべき同一`billings`への2入金の同時登録は、両方が実際に`settled_amount`を書き換えるので変更行だけでも検出できる。
- **消込ステータスは売上明細行のキャッシュ列として持つ（入金明細を都度`SUM`する方式は不採用）**: 元帳表示・明細請求書候補抽出・月次締めの整合性チェックなど、絞り込み表示が頻出するため。
- **キャッシュ列（`sales.settlement_status`／`settled_amount`、`receipts`／`detail_receipts`の`allocation_status`）の書き手は`SettlementService`のみ**: 書き手が1箇所に限られる構造が不整合を作りにくくしている。例外は新規追加行の一時プレースホルダ（未消込／未充当）だけで、いずれも同一トランザクション内で必ず再計算が呼ばれるためプレースホルダのままコミットされない。新しい書き込み経路が再計算呼び出しを漏らすと、全得意先に対する再計算差分ゼロの回帰テストで検出される。
- **締め・明細請求書発行・明細請求書取消は`RecalculateForBillingGroupAsync`を呼ばなくても値が狂わない**: (締め確定) 新しく割り当てる`billing_number`は同一トランザクション内で今作られたものでそれを指す`receipt_allocations`はFK上存在し得ず、`billing_number IS NULL`の行はpool=0扱いなので締め前後でpoolは0のまま。(明細請求書発行) 発行直後の請求書を指す`detail_receipts`はFK上存在し得ずpool=0で、連携前後の結果が同じ。(明細請求書取消) 連携先がすべて未消込であることを既存ガードが強制しており、連携解除前の値が既に0。一方、締め解除と売上の訂正・取消は呼ぶ（解除で`billing_number`が外れた行は充当先を失い未消込へ戻る／金額を減らす訂正で消込済金額が新金額を超えて取り残されるため。一部消込は編集ロックされず金額減額の訂正ができる）。

### 配分アルゴリズム・消込対象額

- **`SettlementAllocator`は3分岐（pool=0／全額充当／不足）にする**: 「マイナス行を先に全額充当してその分を残額に戻す」素朴な方式は、入金が全く無い（pool=0）場合でも返品行だけが消込完了になる事故を起こし、売上の編集ロック（消込完了）と明細請求書候補除外に波及する。(1) pool=0→全行0。(2) 対象額合計がpoolと同符号かつ`|pool| >= |対象額合計|`→返品・値引行を含め全行を対象額どおりに配分（超過分は行に載せない）。(3) 不足→poolと同符号の行だけに、呼び出し元が整列した順（伝票日付→伝票番号→行番号の古い順）で配分し、符号が異なる行は0のまま据え置く（返品行の消込には全額充当が必要という業務上の前提に合う安全側の挙動）。
- **消込対象額は売上明細行の`amount`をそのまま使い、消費税分は行に載せない**: 請求単位・伝票単位（外税）は税抜、内税明細単位は`amount`が既に税込。例: 明細6,000円＋4,000円（税1,000円）の請求に11,000円入金しても、消込対象は10,000円で税額1,000円分は行に載らない。
- **振込手数料差額は消込済金額に含める（行への充当額＝`allocated_amount + fee_adjustment_amount`）が、入金側の`AllocationStatus`判定には含めない**: 入金側の状態は実際に受け取った金額の消化状況を表すため。入金9,780円＋手数料差額220円で請求10,000円が消込完了になる。
- **振込手数料差額は手入力のみで、自動計算・自動補正提案は行わない**: 手入力なのでしきい値等の自動判定ロジックが不要になる。理由: 手入力に決めた理由そのものは要確認（記録なし）。手数料差額を残高からどう落とすかは業務判断が残っており、非ゼロになると元帳の残高に残渣が残りうる。
- **都度得意先は「直接指定（売上明細行を名指し）」を先に確定し、残額（`amount − 直接充当額`）を明細請求書経由の配分に回す**: 1つの売上明細行が両方から同時に充当されうるため、名指しした明示的な指示をシステムが行う配分（導出）より優先する。

### 締め入金（`receipts`／`receipt_allocations`）

- **締め得意先の入金画面には充当先（どの請求にいくら充てたか）を出さず、請求残高だけを表示する**: 利用者にとって重要なのは充当先ではなく残高であるため。充当は保存時に内部で自動配分し`receipt_allocations`へ保持する。
- **`receipts`の明細行は支払手段の内訳（入金方法＋金額＋行摘要）とし、請求への充当（`billing_number`／`allocated_amount`／`fee_adjustment_amount`）は`receipt_allocations`へ分離する**: 1回の入金が複数の支払手段（現金・振込・手形等）に分かれ入金方法は行ごとに選べる必要がある一方、支払手段の内訳の件数と充当先の請求の件数は一致しない（入金2行を3件の請求へ古い順に充当）ため、同じ行に両方の意味を持たせられない。入金先口座・手形期日も行単位の値になる。
- **`receipts`自体は`billings`へのFKを持たない**: 充当先は`receipt_allocations`（`billing_number`）が持ち、`billings`の`UNIQUE (billing_number, tax_unit)`を複合FKで参照するのは`sales`と`receipt_allocations`。`billing_number IS NULL`（前受・過入金）はFK検査対象外でそのまま表現できる。
- **`receipt_allocations`から`receipts`へFKを張らない**: `receipts`のPKが複合（`receipt_slip_number`, `line_number`）で、`receipt_slip_number`単独の一意キーが無いため。`receipt_allocations`は`receipts`と独立した行番号体系を持つ。
- **`receipts`の訂正は金額・入金方法・行の追加削除すべて自由**: 候補概念が無く充当は完全に内部自動計算のため。

### 明細入金（`detail_receipts`）

- **`receipts`（締め入金）と`detail_receipts`（明細入金）は別テーブルのまま統合しない**: 明細入金は「売上伝票または明細請求書を指定したピンポイント消込」で、請求単位で古い順に自動消込する締め入金とは保持すべきカラム（`target_type`分岐・充当先2種）が異なる。税単位が同じでも構造まで同じとは限らない（`sales`／`receipts`／`billings`を統合した判断との違い）。
- **`detail_receipts`の充当先（`target_sales_slip_number`等）は`tax_unit`を含む複合FKにしない**: `detail_receipts`側にも`tax_unit`を持たせる非正規化が増えるため、単純な`(sales_slip_number, line_number)`参照に留め、`tax_unit=3`への絞り込みはアプリ側の抽出条件で行う。
- **明細入金の候補条件は「未消込または一部消込」（売上伝票タブの候補金額は残額`amount − settled_amount`）**: 未消込のみだと、一部消込済みの行が売上タブにも請求書タブ（連携行が全行未消込が条件）にも出せなくなり、残額を永久に入金できない行き止まりができる（手数料調整・部分訂正・データ補正等で一部消込は発生しうる）。
- **明細入金の`Σallocated_amount`（＝`receipt_amount`）が0以下になる保存は拒否する**: `AllocationStatusCalculator`は合計0を「未充当」と判定するため、合計0の伝票は永久に充当完了にならない。行単位のマイナス（返品・値引行の直接指定）は許可して正の行との差引を認めるが、返品行単独・返品合計が正の行を上回る場合は拒否される（その返品は将来の売上と相殺するまで未消込のまま残る。返金処理ではないという業務判断）。
- **残額0の売上明細行と`total_amount = 0`の明細請求書は候補から除外する**: `SettlementStatusCalculator`はamount=0の行を常に「未消込」と判定して消込完了にならないため、直接指定すると明細請求書取消の消込済みチェックをすり抜けたまま明細入金だけが残る不整合を作れてしまう。
- **保存時に`detail_invoice.total_amount == Σ(連携先売上明細行のamount)`を照合し、不一致なら丸めずに拒否する**: 発行時の計算式から常に一致するはずだが、データ補正等でズレた場合に自動で丸めるより拒否するほうが安全（明細請求書発行が税額で同じ防御をしている前例に合わせる）。
- **明細入金の入金方法選択肢から手形（`requires_bill_due_date=1`）を除外する**: `detail_receipts`に`bill_due_date`列が無く、手形を選べると期日情報が保存できずに欠落するため。手形期日列を持たせない（DDL変更なしで完結させる）。振込以外の行は`bank_account_code`を必ず`null`にする。
- **明細入金の明細行金額は読み取り専用（常に対象の全額または残額）で、明細請求書タブは請求書まるごと1行**: 明細請求書の一部の売上だけ入金があったケースは請求書タブではなく売上伝票タブから該当売上明細行を個別に取り込んで対応する（直接指定を先に確定して残額を請求書経由へ回す設計のため併用は正しく処理される）。前受金（充当先NULLの行）は作らない（理由: 要確認（記録なし））。
- **`detail_receipts`に一意制約を付けない**: 付けると部分入金・残額充当が壊れるため。同一売上明細行への同時全額入金は、再計算が`Sales`行をtracking付きで更新するので、後にコミットする側がrowversion不一致（`SlipConcurrencyException`）で弾かれ、追加のロックは不要。
- **明細請求書タブの「この請求書を指す明細入金が存在しない」条件には`!IsDeleted`を付ける**: 付けないと、取消済みの明細入金がその請求書を永久にブロックする。
- **明細入金の訂正で変更できるのは入金日付・伝票摘要、各行の入金方法・入金先口座・行摘要、行の削除のみ。充当先の追加はできない（別伝票で登録する）**: 訂正用の行入力型が`TargetType`等の充当先フィールドを持たず、シグネチャ上も追加不可能。
- **明細入金の訂正では既存行の`AllocatedAmount`／`FeeAdjustmentAmount`を再計算せず読込時の値を保持し、候補判定クエリも再実行しない**: 候補クエリは自伝票自身の充当を除外する仕組みが無く、(1) 明細請求書指定の行は自分自身が「この請求書を指す未削除の`detail_receipts`」として存在するため常に自分自身で弾かれ、日付だけの訂正すら失敗する。(2) `settlement_status`は他の入金の登録・取消で変動するキャッシュ列のため、訂正と無関係にこの伝票の充当額が動いてしまう。
- **明細入金の訂正で全行削除は拒否する（取消を案内する）／訂正後は生き残る全行へ`Σ AllocatedAmount`を`receipt_amount`として書き直す**: 一部の行だけ論理削除すると、伝票単位の全行同値の不変条件（`receipt_amount`）が崩れるため。
- **`UpdateAsync`は全行を論理削除して作り直す方式を採らず、行単位の差分方式にする**: `SlipConcurrencyGuard.EnsureLineSetUnchanged`で検証した行がそのまま更新対象になっているという保証を保つため。

### 入金方法マスタ

- **入金方法（現金・振込・手形・相殺等）は`deposit_methods`マスタで管理する（`ReceiptMethod` enumを使わない）**: enumのハードコードでは、入金方法の追加・改称のたびにコード修正・再ビルドが必要になるため。
- **付随項目の必須（振込＝口座必須／手形＝期日必須）はマスタのフラグ（`requires_bank_account`／`requires_bill_due_date`）で表し、「入金方法によりどちらが必須か」はアプリ層のみで担保する。DBのCHECKは「口座と期日が同時に埋まらない」（`CK_receipts_bank_account_bill_due_date_exclusive`）のみ**: 前者は他テーブル（`deposit_methods`）参照が必要でCHECK制約では書けないため。
- **トリガーは作らない**: このリポジトリにトリガー・ユーザー定義SPは1つも無く、rowversion楽観的排他制御・`SlipConcurrencyGuard.TouchAll`との相性が悪いため。
- **入金方法名のスナップショットは持たない**: 帳票に入金方法名を印字する要件が無く、`customer_name`のような「発行当時の名称を固定する」要件も無いため。元帳は都度`deposit_methods`を読み、`IsDeleted`で絞らない（過去の入金が無効化済みの入金方法を参照していても名称解決できるように）。再検討条件: 発行当時の名称固定が必要になったとき。
- **列名は`deposit_method_code`（varchar(10)、FK）**: 型と意味の両方が変わるため旧`receipt_method`（tinyint）と同名維持は混乱を招く。FK列の命名規約（`bank_account_code`等の`<マスタ名>_code`）にも揃える。

### 締め得意先の請求集約に関わる消込・元帳

- **請求集約先の請求集約グループでは、請求集約元の売上・入金も含めて消込・締め・元帳を計算する**: 請求集約元に入金が入らない前提は入力ガードに過ぎず、過去に単独で入金を受けた得意先が後から請求集約元へ変更されうる（変更可否判定は`receipts`の有無を見ない）ため、消込・請求締め・元帳のすべてで`receipts`もグループへ展開しないと残高が`billing.current_billing_amount`と食い違い、その入金がどの元帳にも現れなくなる。

## 編集ロック・取消

### 訂正・取消の方式

- **訂正・取消は元伝票の直接修正とし、赤伝（マイナス伝票）方式は採用しない**: 理由: 要確認（記録なし）。
- **伝票を物理削除しない（伝票の取消は`is_deleted`で表す。訂正で一覧から消えた行も`IsDeleted=true`）**: 誰がいつ取消したかを監査列で追跡するため。マスタは論理削除、伝票は物理削除しない方針と揃える。F8は物理削除ではなく取消として扱う。
- **訂正で既存行の行番号は詰め直さず、新規行は現在の最大行番号＋1で採番する**: 主キーが(伝票番号, 行番号)のため。
- **訂正は`ApplyLineValues`（ホワイトリスト）で上書き可能な列だけコピーする**: 得意先コード・税区分・請求/消込関連の状態カラム・監査列は対象外。`BillingNumber`は`CreateAsync`だけが無条件にNULLにする方針を維持し`UpdateAsync`は一切触らない。既存行のコピー時の`IsDeleted = false`明示設定の理由は「トランザクション・採番・非同期」節の保存失敗後のChangeTracker汚染の項を参照。
- **売上訂正の税額確定（`SalesTaxAmountAssigner`）には`IsDeleted=false`の行だけを渡し、全行削除なら呼ばない**: 取消済み行を含めると伝票単位の合計税額・内税明細単位の行別税額が狂うため。全行削除は`CancelSlipAsync`と同じ状態になる。

### 売上の編集ロック

- **`sales`の編集ロックは4条件（請求締め／明細請求書発行済み／月次締め／入金済み＝消込完了）のいずれかに該当する場合のみ。伝票側にフラグ（カラム）を持たず、`billing_number`が確定済み`billings`を指すか・`monthly_closings`（得意先＋伝票日付の年月）・連携テーブルの有無・`settlement_status`（キャッシュ列）から導出して判定する**: フラグにすると締め・解除のたびに大量の伝票行を更新することになるため。締め処理自身による状態カラム更新はユーザー編集ではないのでロック対象外（ユーザーの直接編集のみ対象）。
- **明細請求書発行済み（`detail_invoice_sales_lines`に連携済み）を売上の編集ロックに含める**: 都度得意先（`tax_unit=3`）の`billing_number`はCHECK制約で常にNULLのため請求締め条件が発火せず、明細請求書を発行済みでも自由に訂正・取消できてしまい、(1) `detail_invoices`ヘッダーの確定金額スナップショットが実データと乖離する、(2) 行を論理削除しても連携行が残り`IsDeleted=true`の売上を指し続ける、ためロックする。判定順は請求締め→明細請求書発行済み→月次締め→消込完了。
- **編集ロック判定は、判定ロジックをDomain純粋関数（`SalesEditLockEvaluator`）、DB照会（`monthly_closings`／`detail_invoice_sales_lines`）をApplication層の`SalesEditLockService`に分ける**: DB照会をDomainに持ち込まないため。理由文言を返すのみで、ViewModelは業務判断をせずそのまま表示する。
- **売上の訂正は、訂正前だけでなく訂正後の状態でも編集ロックを再判定する**: 伝票日付を確定済みの月次締め年月へ動かす訂正を防ぐため。
- **請求集約元の売上のロックは無改修で効く**: `SalesEditLockEvaluator`は売上行自身の`billing_number`を見る設計のため、請求集約先の請求番号が書かれればそのままロックされる。

### 入金の編集ロック

- **`receipts`・`detail_receipts`には`sales`の4条件をそのまま適用せず、別条件にする**: 入金は保存直後にほぼ必ず充当完了になるため、条件④（入金済み＝充当完了）を適用すると訂正・取消できる入金がほぼ存在しなくなる。請求締めの条件（`receipt.billing_number`基準）も、充当を`receipt_allocations`へ分離した現スキーマでは使えない。
- **`detail_receipts`のロック条件は月次締めのみ**: `detail_invoices`の金額は`sales`から都度導出され、`detail_receipts`からスナップショットを焼き込まれないため、締め請求のような追加ロックは不要。
- **`receipts`のロック条件は月次締めに加えて「請求締めスナップショット」（`receipt_date <= その得意先の確定済みbillingのうち最新のbilling_date`）**: 請求締めが期間内の`receipt.Amount`合計を`billing.current_billing_amount`へ焼き込み以後誰も再計算しないため、この期間の入金を無条件に取消・訂正すると確定済み請求の残高が二重に増減し、`receipt_allocations`から都度計算する現在値と`billing.current_billing_amount`が永久に食い違う。訂正・取消したい場合は該当`billings`を締め解除してから行う。最新の確定済みbillingのみ解除できる制約と整合する。
- **入金の編集ロック判定は専用クラスを作らず、各サービスのpublicメソッド（`EvaluateEditLockAsync`）にする。結果の型は`SalesEditLock`を再利用する**: 判定条件が日付と`monthly_closings`／`billings`の突き合わせの数行で、複数エンティティのプロパティを見る分岐ロジックが無く、抽出しても再利用先が無いため。
- **得意先の付け替えは入金の訂正モードでも常に不可**。
- **編集ロックは既存行の編集・訂正のみを対象とし、新規登録・日付変更で締め済み期間に入り込むことは別機構（日付制限）が防ぐ**: 対象が異なるため。

### 締め済み判定・日付制限

- **編集ロック判定クラスと日付制限判定クラス（`BillingClosedDateEvaluator`／`BillingClosedDateService`）は判定結果を共有せず別クラスにする**: 境界日付（確定済み`billings`の最新`billing_date`）は同じだが、責務（既存行の編集ロック／新規登録・日付変更の入口）が異なり、文言・利用箇所が独立に変わってよいようにするため。境界を問い合わせるクエリの重複は許容する。
- **日付制限の最小日付は「確定済みbillingの最大`billing_date`＋1日」で、確定済みbillingが無ければ制限なし。解除済みは対象外**: 締め解除すればその期間に再登録できるという締め解除運用と整合させる。都度得意先は`billings`を1件も持たないため、税単位で分岐せずとも自動的に無制限になる。対象は売上入力・入金入力のみで、明細入金・受注は対象外。請求集約元は`billings`を持たないので、請求集約先を解決してから`billings`を引く（引かないと確定済み請求期間へ請求集約元の売上を遡及登録できてしまう）。
- **日付制限の強制は保存時のApplication層で行い、画面の`DatePicker.DisplayDateStart`は利便性のみ（`BlackoutDates`は使わない）**: `DisplayDateStart`はカレンダーのマウス選択しか制限せず、8桁ベタ打ち入力が`SelectedDate`を直接代入する経路を迂回できる。`BlackoutDates`は範囲外日付の`SelectedDate`代入で例外を投げ、訂正モードの読込・複写がクラッシュしうるため採用しない。得意先確定時に現在の日付が最小日付より前なら自動補正して通知し、既存伝票の読込では日付を書き換えない。取消は日付を変えないので対象外。
- **月次締めの日付検証は`DisplayDateStart`を付けず保存時のエラーメッセージで知らせる**: 締め済みの月が飛び飛びになり、許可日が連続にならず単一の最小日付という設計と相性が悪いため。
- **月次締め済み判定は、対象得意先C・日付Dについて「Dの月末日の`monthly_closings`確定行が、C自身またはCの請求集約先のもの」があれば締め済み（`MonthlyClosedService.IsClosedAsync`に集約）**: 請求集約先の月次行はグループ全体（請求集約元の売上・入金）を含むため、請求集約元に自分の月次行が無くても請求集約先が確定済みなら請求集約元の売上・入金も登録・訂正・取消できない。解除済みは含めない。訂正による日付変更は訂正後の状態での編集ロック再評価が同じ判定を使うので追加検証は不要。都度得意先も月次締めの対象なので税単位では分岐しない。受注は月次締めの対象外。

### 締め解除・月次締め解除

- **締め解除・月次締め解除は、権限差が出る操作のため、請求締め・月次締め本体とは別画面（別メニュー項目）にする**: メニュー単位の権限レベル判定だけで権限を制御し、画面内アクション単位の権限判定は行わない（請求の締め解除・月次締め解除とも権限レベル9のメニュー登録）。
- **月次締め解除は指定年月の確定済み行を全得意先まとめて解除するAll-or-nothing（1件でも解除できないものがあれば何も更新せず中止）。解除できない条件は、その得意先により後の年月の確定済み行があること（請求締め解除の「最新のものだけ」と同趣旨）**: 解除すると後の月の前月残高（前月確定行の当月残高）とのつながりが切れるため。新しい月から順に解除する運用になる。得意先1件だけを解除する機能は持たない（必要になれば別途設計）。
- **月次締め解除は`closing_status`を解除済にするのみで物理削除せず、他テーブルも更新しない**: 一度確定した月次残高を追跡できるようにするため。編集ロックは導出方式なので、解除すると即座にその月の伝票を再登録・訂正・取消できる。再確定は月次締め処理が解除済みの行を上書きして確定に戻す（主キーが同じで新しい行を作れないため）。

### 受注

- **受注は未売上（`order_status`＝未売上）の伝票のみ直接修正でき、一部売上・売上完了・中止済みは読込できるが修正できない。中止（伝票単位）は一部売上でも可能**: この非対称は意図した仕様（`OrderEditLockEvaluator`）。理由: 非対称の根拠そのものは要確認（記録なし）。
- **`OrderEditLockEvaluator`はDomain純粋関数のみで、Applicationラッパー（`SalesEditLockService`相当）を作らない**: 売上がラッパーを持つのは`monthly_closings`・`detail_invoice_sales_lines`のDB照会をDomainに持ち込まないためで、受注の判定条件は明細行自身の`order_status`のみで外部照会が不要なため、転送しかしないクラスを新設する理由がない。`OrderService.UpdateAsync`と`OrderEntryViewModel`が直接呼ぶ（判定式の正が1箇所にあれば「ViewModelは業務ルールを判断しない」の趣旨を満たす）。判定順は中止済み→売上完了→一部売上で、状態ごとに文言を変える。
- **受注の中止は伝票単位の操作で、明細行単位の中止APIを作らない**: 業務上の失注・キャンセルは伝票丸ごとが通常のため。
- **中止は終端状態で解除しない（誤って中止した場合は新規に受注を入力し直す）**: 理由: 解除を作らない理由そのものは要確認（記録なし。運用でカバーする方針のみ記載）。
- **`CancelSlipAsync`は`SalesConfirmedQuantity`を変更しない**: 分納済みの実績を残すため。売上完了済みの明細行を含む受注・既に中止済みの受注の中止は拒否する。
- **中止済み受注の明細行への負のデルタ（売上取消）は許可し、正のデルタ（売上化）は拒否する。状態は`Cancelled`のまま維持し未売上／一部売上へ戻さない**: 「一部売上化→受注を中止→その売上を後から訂正・取消」の順序が起こり得るため、負のデルタを一律拒否すると売上側の取消が永久にできなくなる。
- **返品・値引行は受注に紐付けられない（`SalesService`が拒否）。受注由来の売上を返品したい場合は元の売上行を直接訂正する**: 受注の売上化済数量を減算するのは売上行のみのため。受注デルタは`(受注伝票番号, 受注行番号)`ごとに合算してから渡す（同一受注行を複数の売上行が参照しても重複キー拒否に当たらないように）。
- **受注の訂正で全行削除は拒否する（中止を案内する）**: 売上の訂正は全行削除が`CancelSlipAsync`と同じ状態になり許容されるが、受注の中止は`is_deleted`ではなく`order_status = Cancelled`で表すため、全行を`IsDeleted = true`にすると`OrderQueryService`のどの照会にも見えなくなり、`CancelSlipAsync`も0件ヒットで「受注が見つかりません」となり、中止すらできない伝票になる。
- **受注の`UpdateAsync`は明示トランザクションを開始しない（暗黙トランザクションで足りる）**: 採番せず、他サービス（受注デルタ適用・税額確定・消込再計算に相当するもの）も呼ばず、`SaveChangesAsync`が1回のため。
- **受注の訂正後の編集ロック再判定はしない**: 受注のロック条件は`order_status`のみに依存し、`UpdateAsync`は`order_status`を書き換えず新規行も未売上固定なので、訂正後の状態は定義上ロック対象になり得ない（売上は伝票日付が月次締め年月を跨ぐ条件があるため再判定する）。
- **受注の訂正で税額確定・消込再計算を行わない**: `orders`は税額列を持たず、消込の概念もないため。
- **受注の訂正で`OrderQuantity >= SalesConfirmedQuantity`の検証を書かない**: 修正可能なのは未売上限定（`SalesConfirmedQuantity`は常に0）で論理的に到達不能なため。前提が崩れたら未売上でない伝票の保存拒否テストが赤くなる。
- **受注の訂正はホワイトリスト15列（`OrderDate, CustomerName, ProductCode, ProductName, Specification, UnitName, OrderQuantity, UnitPrice, Amount, CostPrice, TaxCategory, TaxRate, SlipRemarks, LineRemarks, InternalRemarks`）のみ上書きする**: `CustomerCode`は変更不可、`SubCustomerId`はUIが値を持たず常にnullで将来復活時に静かに消えるのを防ぐため除外、`AllocatedQuantity`は在庫連携スコープ外、`OrderStatus`／`SalesConfirmedQuantity`の所有者は`OrderStatusService`のみ。
- **受注の訂正モードでは得意先コード欄を`IsReadOnly`にし、得意先検索・コード照会の2コマンドも`CanExecute`で無効化する。得意先名欄は編集可のまま**: 欄をReadOnlyにするだけではSpace/Returnのキーバインド経由で得意先が差し替わってしまうため両方必要。名称はホワイトリスト対象（宛名の都度書き換え）。売上側は得意先コード欄が訂正モードでも編集可で、変更しても黙って無視される既知の不整合が残っている。
- **受注入力画面のSPACE検索では、売上完了・中止済みの受注も表示する（`IncludeUnavailableOrders = true`）。売上入力画面の受注検索は表示しない**: 前者は閲覧・複写目的、後者はこれ以上売上化できない受注を候補に出す意味が無いため。受注複写でも同じ設定にする。

### 返品・値引

- **返品・値引はマイナス数量・マイナス金額の伝票とし、伝票区分（`slip_type`：売上／返品／値引）は明細行ごとに選択する**: 同一伝票内に売上行と値引行を混在できる。`orders`には伝票区分の概念がないので受注入力画面では区分列を非表示にする。
- **値引行も商品コードは必須で、値引専用の擬似商品コードは作らない**: 税率・税種別区分がその商品から決まる必要があり、それがインボイス制度上も正しいため。
- **値引の原価は常に0、返品は商品原価をそのまま使い（原価もマイナス計上）、正規化ロジックは`SalesSlipTypeRules`に集約する**: 値引は現品の移動を伴わないため。返品時に原価もマイナス計上することで元の売上の粗利影響をちょうど打ち消す。`SlipLineViewModel.CostPrice`自体は破壊的に書き換えず、粗利計算と保存時の2境界でのみ正規化を適用する（値引→売上と往復しても原価を失わないため）。
- **数量と金額の符号一致（`Math.Sign(Quantity) == Math.Sign(Amount)`）はApplication層が検証するだけで黙って書き換えない**: 正規化はViewModelの責務。
- **過去伝票の複写（売上・受注）は、単価は複写元の値を維持し、税率だけ新しい日付（売上日付／受注日付）で再解決する**: 同じ取引条件の再現を優先しつつ、税率は日付時点のものを使うため。伝票番号・伝票日付（当日）・受注リンク・請求/消込/納品書発行状態は複写しない（新規登録の初期値）。
- **返品・値引行（および論理削除行）は商品検索の「過去の取引履歴」タブの単価候補に出さない**: 単価候補として現れないようにするため（`!IsDeleted && SlipType == Sales`）。

## マスタ・宛名・請求集約

- **宛名は伝票入力時の名称上書き（都度書き換え）で実現し、子得意先マスタを作らない**: 学校－学年－クラスのような階層を持つ得意先も、マスタ上は常に1得意先（1レコード）として扱い、学年・クラスの違いは伝票の名称欄の手入力上書きだけで表現する。ジャーナル系の画面（受注・売上・入金・明細請求書等）は得意先コード検索後に名称欄を上書きできる。これが宛名変更の唯一の手段。理由の詳細: 要確認（記録なし。「都度書き換え方式に一本化」とのみ記載）。
- **`sub_customer_id`列は残すが未使用（参照・更新する処理なし）**: 将来の別要件に備えて削除しない。削除しない以外の対応方針はなく、入力欄も作らない。
- **`sub_customer_id`（宛名の都度書き換え）と`billing_customer_code`（請求集約）は別概念として扱う**: 前者は請求書に印字する名称だけを都度差し替える仕組み（マスタ上は常に1得意先）、後者は「どの得意先の売上をどの得意先の請求書に計上するか」という正式なマスタ構造。宛名方式で子得意先マスタを作らない決定は、後者を否定しない。
- **請求集約の関係は「請求集約元／請求集約先／請求集約グループ」と呼び、「親得意先」「子得意先」の語を使わない**: `sub_customer_id`の文脈で使われる「子得意先」と紛れるため。
- **締め対象／都度対象の判定は`closing_day`（0なら都度）のみで行い、専用の区分フラグを持たない**: 現状の業務要件（一般企業＝締め、官公庁・学校・都度取引先＝都度・明細）ではこれで十分なため。
- **請求集約の対象は締め得意先のみとし、都度得意先（`tax_unit=3`）は請求集約元になれない**: 複合FKだけでは「都度得意先どうしの請求集約」を防げないため、`CK_customers_billing_customer_tax_unit`が唯一の防壁になる。請求集約元の請求集約元も不可（階層は2段まで）。
- **請求データ（`billings`）は請求集約先にだけ作り、入金・残高管理も請求集約先に集約する。請求集約元には`billings`を一切作らない**: 請求集約元の売上は請求集約先の請求に取り込み、`sales.billing_number`に請求集約先の請求番号を書く。入金入力画面で請求集約元を指定したら業務例外で拒否する。
- **請求集約の整合をDBの複合自己参照FK（`FK_customers_billing_customer`）で強制し、`billing_parent_root_flag`（常に1の定数計算列）を参照側・被参照側の両方に挟む**: 「指し先が請求集約先自身である」ことをCHECK制約は他行を参照できないため単体で表現できない。この技巧により、指し先の実在・指し先が請求集約先自身（＝2段以上の階層の拒否）・3項目（締日/税区分/端数区分）の一致が同時にDBで強制される。自己参照FKのためON UPDATE/DELETE CASCADEは使えないが、3項目は登録後変更不可・`customers`は論理削除という既存方針と両立し実害はない。
- **複合自己参照FKはEF Coreで表現しない（`CustomerConfiguration`は`billing_customer_code`列のマッピングのみ、計算列2本もエンティティにマップしない）**: `billing_parent_root_flag`が定数列でEFが関係を表現できず、`is_billing_root`はアプリ側で`BillingCustomerCode == CustomerCode`と同じ判定ができるため。罠: EFがFK関係を認識できないため、請求集約先と請求集約元を同一の`SaveChanges`で同時に新規作成できない（挿入順序を解決できない）。得意先マスタ画面は1件ずつ保存するため実運用上の制約にはならない。
- **請求集約のバリデーションをDB制約と二重に持つ（`BillingAggregationValidator`、Domain純粋関数）**: ユーザーへ分かりやすいエラーメッセージをアプリ層で返すため。DB制約は最後の防波堤。
- **請求得意先コードは、確定済み`billings`に取り込まれた売上が1件でもある得意先は変更不可（未請求の間は自由に変更可、`closing_day`等のような新規登録時限定ではない）**: 過去に発行済みの請求書と現在の`sales.billing_number`の対応関係が変わらないことを保証するため。締め解除で`billing_number`がNULLに戻ると再び変更可能になる（締め解除の意味論と整合する）。
- **未請求のままの得意先を請求集約元に変更する場合は、得意先マスタ画面で変更前に確認ダイアログを出す**: 一度も締めていない得意先の未請求売上はすべて次回の請求集約先の請求に合算される（売上抽出に期間下限が無い）が、上記の変更不可判定はこのケースを弾かないため。
- **`CustomerService.HasBillingChangeLockAsync`は`receipts`の有無を見ない（既知の穴。塞いでいない）**: 過去に単独で入金（前受金・締め解除後の入金残）を受けた得意先を後から請求集約元へ変更できてしまう。その入金が請求額・消込・元帳から漏れないよう、`BillingClosingService`・`SettlementService`・`CustomerLedgerQueryService`の側でグループ全体の`receipts`を対象に広げて吸収している。`HasBillingChangeLockAsync`に`receipts`チェックを足す案は見送り（新規に請求集約元へ変更する入口対策としては将来検討の余地あり）。
- **請求・入金・消込・残高の処理は、スコープキーを「得意先」から「請求集約グループ」（請求集約先＋全請求集約元）に広げる。売上・受注・納品書・商品単価履歴など伝票そのものを扱う処理は`customer_code`単位のまま変えない**: 納品書は実際に納品した請求集約元宛に出すのが正しく、商品単価履歴も請求集約元ごとの購買実績を見るべきため。
- **元帳・月次締め・実績集計は請求集約元（`customer_code`）ごとの個別集計を維持し、残高・請求・入金だけを請求集約先に集約する**: 得意先元帳・月次締めは会計上の売掛金集計であると同時に支店別営業実績（担当者別売上・粗利。担当者は`sales.employee_code`）の集計単位でもあり、請求集約先に合算すると支店別実績が失われるため。月次締めの請求集約元の行は自社売上と税率別対価額のみで、`previous_balance`・`tax_amount`等は0。
- **消込（`SettlementService.RecalculateForBillingGroupAsync`）はグループの得意先コード集合を対象にする**: 単独得意先のスコープのままだと、グループ全体の入金額と請求集約先単独の売上額を比較して`SettlementAllocator`の全額充当分岐が誤って成立し、請求集約先の売上が実際には未入金でも消込完了になり、請求集約元の売上は永久に未消込のまま残る（金額の実害）。単独得意先（当面ほぼ全件）は従来どおり等値比較のまま、2件以上のときだけ`Contains`に分岐し、実行計画を変えない。
- **請求集約グループへ展開しても消込の配分ロジックは無改修で成立する**: グルーピングキー（`billing_number`／`receipt_slip_number`）と整列キー（`sales`の主キー）がいずれも全社で一意（得意先単位でない）ため、対象クエリの絞り込みを「対象得意先コード」から「グループの得意先コード群」に変えるだけで、請求集約先・請求集約元の売上が自然に1グループとして扱われる。請求締めの`CalculateTaxSummary`も同様（伝票番号が全社一意で1伝票=1得意先のため、グループ内の複数得意先の行が混ざっても伝票ごとの税額再計算は汚染されない）。
- **請求締めはグループ合算してから税額を1回だけ丸める**: 個別に丸めると請求集約先・請求集約元それぞれの丸めの合計とずれる（例: 105円ずつの売上で個別なら10+10=20円、合算なら210円→21円）。締め対象の候補は請求集約先（または単独得意先）のみ。請求集約元を候補に含めると、請求集約元が自分自身の`billing`を単独で確定してしまう。
- **`BillingClosingService`の前回請求・前回残高の照会（`billings`）は対象得意先自身のコードのまま**: `billings`は請求集約先にしか作られないため、対象がすでに請求集約先であればこれ以上広げる必要も広げてはいけない理由もない。`BillingReleaseService`（締め解除）は無改修で成立する（売上の紐付け解除が`billing_number`の所属だけで判定され`customer_code`で絞らないため、請求集約元の売上行も拾われる）。
- **請求日付制限（`BillingClosedDateService`）は、`billings`を引く前に対象得意先の請求集約先を解決する**: 請求集約元には`billings`が存在しないため、自身の`billings`しか見ないと確定済み請求期間へ請求集約元の売上を遡及登録できてしまい、次回締めに取りこぼしが混入する実害がある。
- **入金入力で請求集約元を拒否するチェックは、ViewModelの事前チェックとサービスのthrowを二重に持つ**: 既存の都度得意先拒否と同じ作法。ViewModelにエラー表示の共通ヘルパーが無く、事前チェックを欠くと検索モーダル経由の入力がfire-and-forgetで例外を握り潰すため。
- **得意先元帳は、請求集約元では取引履歴（売上）のみを表示し、残高・繰越・消費税・入金を出さない**: 残高が常に未回収のように見えてしまうため。「請求・消費税・残高は請求集約先に集約」と案内する。`GetBalanceAsOfAsync`は請求集約元に対して0ではなく`null`を返し、残高0円と区別する。請求集約先の元帳は配下の請求集約元の売上と入金を含めて表示する（残高を正しくするため必須）。
- **元帳の時系列には請求集約元ごとのまとまりを作らない（`SortKey`に得意先コードを足さない）**: 同日行を得意先ごとにまとめると残高が日付順に読めなくなるため（請求書帳票は逆に得意先コード順にまとめる）。元帳の得意先欄は常時表示（`GridViewColumn`に`Visibility`がなく条件付き非表示は割に合わないため）。
- **明細行は非正規化し、ヘッダー相当（得意先・日付等）を各明細行に持たせる（ジャーナル単独完結）**: 売上・入金は会計上のジャーナル（確定したら修正できない記録）でもあるため、明細行単独で完結した記録である必要がある。受注は状態が変化する仮伝票でジャーナル性はないが、テーブル構成の一貫性・実装の単純さを優先して同じ1テーブル構成に統一。罠: 伝票単位の値（伝票日付・得意先コード・入金額・伝票単位の消費税額・摘要）は同一伝票の全行に同値が入るため、`SUM`すると行数だけ多重計上される。伝票単位で1行に絞ってから扱う。
- **伝票摘要（`slip_remarks`）・社内摘要（`internal_remarks`）は同一伝票の全明細行に複写し、集計で`SUM`しない**: `slip_date`／`customer_code`と同じ伝票単位の値。社内摘要（受注・売上のみ）は画面表示専用で納品書には印字しない。ヘッダーのみの集計テーブル（`billings`／`detail_invoices`）はジャーナルではないため摘要列を持たない。
- **商品の単価決定ロジックのみ、差し替え可能なインターフェース（`IUnitPriceCalculator`／現行実装`StandardUnitPriceCalculator`）にする（「将来の差し替えを見据えた抽象化は行わない」既定方針の例外）**: 将来、掛け率マスタを実装する予定があるため。掛け率マスタ実装時はDI登録の差し替えだけで対応する。現時点で単価計算マスタは作らず、得意先の`tax_unit`に応じた外税単価／内税単価を初期値として転記し手入力で上書きする。
- **原価は商品マスタの標準原価を転記する（暫定）。商品検索の「過去の取引履歴から」軸で選んだ場合も、履歴行の原価ではなく商品マスタから取り直す**: 仕入機能がスコープ外のため。粗利計算には現在の標準原価を使う方針。過去実績原価での粗利計算が必要になった場合は`ProductSearchDialogViewModel.AddHistoryToBasket`を直接修正する。再検討条件: 仕入機能を実装する際に最終仕入原価・移動平均等へ見直す。
- **税率は施行日付きの`tax_rates`マスタで持ち、Domain層の定数にしない。伝票登録時に伝票日付以前で最新の適用開始日のレコードから引いて伝票へ転記する**: 税率改定にコード修正なしで追従するため。終了日は持たない（次のレコードの適用開始日の前日までで決まり、隙間・重複が生じない）。転記後は伝票側のスナップショットとして残り、マスタ改定が既存伝票に影響しない。非課税は本マスタを参照せず税率0を転記。税種別区分の識別子・カラム名に具体的な税率（%）を書かない（税率改定で名称が実態と食い違うため）。
- **売上を1系列（`sales_slip`）で採番し、税単位ごとに分けない**: 伝票番号が得意先の税区分によって別系列になると、現場で伝票番号から伝票を探すときに混乱するため。
- **伝票番号は接頭辞なしの8桁ゼロ埋め**: 伝票番号は`varchar`列であり、文字列ソートが数値ソートと一致する必要があるため（`ProductHistoryQueryService`等が伝票番号で文字列ソートしている）。罠: 8桁を超えると文字列ソート順が壊れる（`"99999999" > "100000000"`）が、1日あたりの伝票発生数から現実的でないため許容し、上限チェックは置かない。再検討条件: `ORDER BY`を伝票番号に依存する画面が具体化した時点。
- **採番テーブルは`row_version`を持たず生SQLの`UPDATE ... OUTPUT`で直列化し、EF Coreで追跡しない**: 楽観的排他は競合時にリトライが必要で採番の直列性と相性が悪い。追跡した状態で読むと別セッションの採番結果を古い値で上書きしうる（`row_version`が無くEFが検出できない）ため、参照は必ず`AsNoTracking()`。
- **伝票番号の重複禁止の最終防衛線は明細の複合主キー（伝票番号, 行番号）なので、主キーを単一列に変えない**: 万一採番が重複しても、行番号が両方1から始まるため2件目のINSERTが必ず衝突して拒否される。
- **コピー機売上CSV取込は、CSV1行ごとに `SalesService.CreateAsync` を1回呼び（1行＝1トランザクション）、全件のAll-or-nothingにしない**: `CreateAsync` が採番を含む自前のトランザクションを持ち外側トランザクションを受けない。失敗行だけをエラー表示して他行は登録し、再取込は `copier_import_histories` の主キー（機番＋締日）で二重取込を防ぐ。履歴INSERTは売上と同一トランザクションに入れる。
- **取込用の売上は汎用商品1件（暫定）にまとめる**: `sales.product_code` が必須かつ商品マスタへのFKでフリー入力の行が作れないため。機種・料金区分ごとの商品分けは要望が出た時点で `copier_machines` に商品コードを足す。
- **CSVは列名で引く**: メーカー出力は約70列あり並びが変わりうるため、位置ではなくヘッダー名で必要列だけを読む。

## 帳票

- **帳票はWPFの`FixedDocument`/`FixedPage`をC#で直接組み立て、QuestPDF・RDLC・Crystal Reports・FastReport等の外部帳票ライブラリ・デザイナーを使わない**: QuestPDFの無償Community Licenseは「年間売上高$1M未満の企業」限定で、石山商店が該当するか確認が取れず、該当しない場合は有償ライセンスが必要になるため。またPDF保存・メール送付は「都度ユーザーがボタンを押して保存先を選ぶ」運用でよく、その場合はOS標準の「Microsoft Print to PDF」仮想プリンタで足りて追加ライブラリ・ライセンスが不要になる。再検討条件: 複数件をダイアログなしでPDFファイルとして自動生成・送信する必要が出た場合（一括発行画面での利用など）は、QuestPDF等の導入を再検討する。「納品書一括発行」は複数件の印刷を指し、PDFの自動生成を指さないという理解で進めている。
- **出力経路は、設定済みプリンタへの直接印刷（ダイアログなし、基本経路）と、「PDF保存」ボタンから「Microsoft Print to PDF」へ印刷する経路の2つで、どちらも同じ`FixedDocument`を使う**: プリンタの選択は帳票種別ごとの設定済みプリンタ（`PrinterSettingsConfig`）を踏襲する。PDFの保存先はOS標準ダイアログに任せ、1件ずつ保存する。
- **`ReportPrintService`はSingletonでDbContextに依存しない**: `PrinterSettingsService`と同様に、プリンタ設定がDBではなく端末ごとの`bmcs_config.json`に保存されるため、DBスコープを持たないサービスとして揃える。
- **プリンタ設定は端末ごとに`bmcs_config.json`（実行ファイルと同じフォルダ）へ保存し、DB管理しない**: 理由: 要確認（記録なし）。
- **印刷・PDF出力とも`PrintTicket`の用紙をA4・縦向きに固定する**: プリンタの既定用紙がLetterの端末で縮小・欠けが起きるのを防ぐため。A4寸法は210mm×297mmを正確に変換した793.7008×1122.5197 DIUを使う（別リポジトリの先行実装の793.92/1122.24は正確なA4とずれる）。
- **印刷は設定済みプリンタへダイアログなしで直接送信し、失敗したときだけ`PrintDialog`にフォールバックする。エラー表示は`ReportPrintService`内で行わず、`ReportPrintResult`で返して呼び出し元がStatusMessageに表示する**: 通常運用ではダイアログを出さない方針のため。
- **プレビュー画面（`ReportPreviewDialog`）は`FixedDocument`を使い回さず、表示・印刷・PDF保存の都度`Func<FixedDocument>`で作り直す**: `FixedPage`は1つのビジュアルツリーにしか属せないため。プレビューは特定帳票の知識を持たない全帳票共通の画面にする。
- **`DocumentViewer`の組込ツールバーを使わず、`ControlTemplate`を`PART_ContentHost`だけの`ScrollViewer`に絞って、印刷・PDF保存・閉じるを自前ボタンにする**: 既定ツールバーの印刷ボタンは標準の印刷ダイアログを開き、「ダイアログを出さず設定済みプリンタへ直接送信する」方針と矛盾するため。
- **帳票の`TextBlock`は`Foreground = Brushes.Black`を明示する**: 明示しないとMahApps.Metroのウィンドウテーマ色（濃灰）を継承して印字が薄いグレーになり、画面プレビューだけでなく実際の印刷・PDFにも影響するため（`ReportDocumentBuilder`の`Tb()`・明細テーブルの生成箇所）。
- **`ReportDocumentBuilder`（描画プリミティブ）と、改ページ付き単一フロー帳票のテンプレートメソッドを持つ`PagedReportDocumentBuilder`に分割する。請求書・明細請求書は後者を継承し、納品書は前者を直接継承して自前の`Build()`で3セクションを組み立てる**: 納品書は3段複写という改ページの考え方自体が異なり、後者を継承させると不要な単一フロー用の抽象メンバーを実装させられる歪みが生じるため。

- **自社情報（`CompanyInfo`）が未登録の場合は納品書の印刷を`DeliveryNoteException`で中止する**: 登録番号が発行者情報として欠落した紙を出さないため。
- **納品書の明細は列を増やさず、返品・値引行の商品名に`[返品]`/`[値引]`、軽減税率対象商品に`※`を前置する**: `SlipType`が行単位のため。残余幅の商品名列に収める。
- **納品書に担当者を印字しない**: 担当者は社内の管理情報として登録するだけで、納品書の記載事項としては求められていないため。印字が必要になったら`DeliveryNoteData`・`DeliveryNoteDocumentBuilder`に追加する。

- **無効化された社員は担当者として新たに入力できないが、既存伝票に入っている担当者は表示・保存できる**: 訂正で開いた伝票の担当者が無効化済みでも、利用者が触らない限り値を保つため（社員マスタは論理削除のみで、FKも切れない）。
- **納品書の発行回数は印刷成功時のみカウントし、PDF保存は数えない。`DeliveryNoteIssuedAt`は最終発行日時（上書き、初回日時の履歴は持たない）**: 「Microsoft Print to PDF」はOS側の保存ダイアログをアプリから検知できず、キャンセルされたPDF出力を発行済みとして記録してしまう事故を避けるため。発行回数1以上のときタイトル横に「（再発行）」を表示する。
- **発行記録（`DeliveryNoteService.MarkIssuedAsync`）は編集ロックを適用せず、rowversionの楽観的排他も掛けず、`UpdatedBy`/`UpdatedAt`も更新せず、`ExecuteUpdateAsync`の集合更新で行う**: 請求済・入金済でも再発行できる（再発行は可能という仕様）ため編集ロックは適用しない。発行日時・発行回数は伝票内容ではなく帳簿外の記録列のため楽観的排他は不要。専用の発行日時列があるため、伝票内容を最後に編集した者の記録を印刷操作で上書きしない。一括発行もこのメソッドを再利用する。
- **`MarkIssuedAsync`は更新後に同一スコープの追跡エンティティを`ReloadAsync`で最新化する**: `ExecuteUpdateAsync`はChangeTrackerを経由しないため、同じ`BmcsDbContext`スコープで追跡ありに読み込まれた当該伝票の`RowVersion`がDBの新しい値と食い違ったままになる。SQL Serverの`rowversion`は列の値に関わらずどのUPDATEでも進むため、放置すると次の保存が偽の「他のユーザーが更新しました」エラーになる。

- **請求書・明細請求書は売上明細行ごと（品目別）に印字し、納品書には無い「伝票No.」列を持つ**: どちらも複数の売上伝票にまたがるため。
- **請求書のサマリー（前回請求額・ご入金額・今回売上額・消費税額・今回ご請求額）とフッターの税率別内訳は別に表示する**: フッターの内訳は本請求期間の売上・消費税（`SalesAmount`／`TaxAmount`）に対するもので、前回残高・入金を含む今回ご請求額とは別物のため。
- **請求書・明細請求書は、締め解除済み・取消済みでも印刷を禁止しない（明細0件・ヘッダーの確定金額のみ出る）**: 過去の参照用の印刷を禁止する理由がないため。締め解除は`sales.billing_number`をNULLに戻し、明細請求書の取消は連携行を物理削除する非破壊ヘッダー方式のため明細が0件になる。ただし明細請求書は取消済みを画面の印刷ボタンで選べないようにする（F8の取消可否と対称。取消済みは明細0件で印刷の実用性が低いため）。請求書は画面の一覧が確定済みしか表示しないため、その画面からは解除済みを選んで印刷できない。
- **代表者は、得意先マスタ`print_representative_flag`が真のとき発行者情報ボックスに「代表者　○○○○」＋押印用の空欄枠として印字し、印影画像は持たない**: 自社情報マスタは代表者名のみ保持し印影画像を持たないため。宛名を書き換えても印字要否は変わらず発行元の得意先マスタの設定に従い、明細請求書ヘッダーにも印字要否の列を持たない。
- **請求書の振込先は得意先マスタの`bank_account_code1`／`bank_account_code2`（最大2件）に紐づけて得意先ごとに印字し、全社共通の`is_print_on_invoice`フラグ方式は廃止した（列を削除）**: 得意先ごとに振込先を使い分けたいという業務要件のため。発行元の得意先（請求書は請求集約先）の紐づけを使い、発行者情報ボックスの直下の独立した枠に置く。空欄なら印字しない。同一口座を2件指定できない（`CK_customers_bank_account_distinct`）。
- **振込先の枠は紐づけが0件・1件でも常に「見出し1行＋2行」の固定行数で組み立てる**: 得意先によって帳票のレイアウトがずれないようにするため。
- **振込先は納品書には印字しない**: 理由: 要確認（「従来どおり」とのみ記録）。
- **振込先の口座名義は印字しない（1口座1行＝銀行名＋支店＋種別＋口座番号）**: 理由: 要確認（記録なし）。
- **振込口座は自社情報マスタではなく銀行口座マスタ（`bank_accounts`）で管理する**: 口座は複数持ちうるため、自社情報マスタに1組だけ持たせると銀行マスタと重複する。

- **請求書の印刷履歴は記録せず、「（再発行）」表示も行わない（`billings`／`detail_invoices`にDDL変更なし）**: 理由: 要確認（記録なし。納品書と異なる扱いとのみ記載）。
- **請求書の印刷導線は専用の発行画面を新設せず、請求締め処理画面の一覧から選択行を印刷する。確定後も画面をリセットせず、入力条件・結果一覧を残す**: 確定後に画面をリセットすると印刷対象の請求番号が一覧から消えるため、印刷導線と直接矛盾する。次のバッチに進みたいときは入力条件を変えれば自動再取得で一覧が置き換わる。
- **請求締め処理画面の一覧は、確定前の集計プレビューではなく`billings`に実在する確定済み請求データを請求日だけで抽出したものとする（解除済みは表示しない）**: 集計プレビュー方式では画面を開き直すと既に締め済みのため請求番号なしのスキップ行になり、過去の請求書を再印刷する手段が無くなるため。締め日区分は`billings`に列が無く抽出条件に使わない。解除済みは同一得意先に旧番号と再締めした新番号が並び得て印刷対象の判別がつかなくなるため表示しない。確定前の内容が見えなくなった分、締め確定は実行前に対象件数を示す確認ダイアログを挟む。一覧は拡張選択で複数行を選べ、選択行を1つの`FixedDocument`に連結して1回のプレビューで印刷する（これが請求書の再発行手段。`PrintCommand`は選択の同期を`MultiSelectionBehavior`に任せてパラメータを取らない。`ListBox.SelectedItems`が依存関係プロパティでなく直接バインドできないため）。
- **請求集約の請求書は明細の列を増やさず、得意先の境界に見出し行（商品名列に【コード 名称】）と小計行を挟む**: 「得意先」列を足さずに、どこからどこまでがどの請求集約元の分かを明記するため。`InvoiceReportRowBuilder`（Domain純粋関数）が表示順を組み立てる。
- **集約していない請求書（明細の得意先コードが1種類だけ）は見出し行・小計行を挟まず、既存の単独得意先の帳票をバイト単位で不変に保つ（最重要の回帰防止制約）**: 単独得意先ではCustomerCodeが全行同じ値のため、明細の並び順を得意先コード優先に変えること自体も無害。
- **請求集約の請求書のフッター税率別内訳は無改修で正しい**: `ResolveConfirmedBuckets`が請求集約先の`billings`1件分（請求集約元の分も合算済み）の確定金額を使い、税率ラベルだけを明細行から借りるため、明細が複数得意先混在でも二重丸めが発生しない。
- **`ReportPagination.AvoidTrailingHeaderOrphans`を新設し、既存の`Split`は改修せず、`PagedReportDocumentBuilder.Build()`が`Split`の結果に対して後段で適用する**: 見出し行がページ末尾に孤立して次ページ先頭の明細と離れるのを防ぐため。`Split`のシグネチャを変えず既存の帳票に影響させない。見出し行の直後には必ず明細行と小計行が続く構造のため、調整は1回の走査で足り連鎖的な調整は発生しない。
- **請求集約時は`FullHeaderHeight`を+18.0して「請求集約元: N社」の1行分を確保する。Nは配下の請求集約元（請求集約先自身を除く）の件数で、見出し行の総数からではなく「請求集約先自身のコードが明細に含まれるか」で判定する**: `FullHeaderHeight`が変わると1ページ目の収容行数が再計算されるため、可変にし忘れると最終ページで本文とフッターが重なる。請求集約先自身の売上が請求期間に無く、配下の分だけで請求データが作られるケースがあり得るため。
- **請求書フッターの請求集約元別内訳ブロックは実装しない（任意扱いのまま。`FooterHeight`は無改修）**: 本文の見出し行・小計行だけで「請求集約元ごとの内訳が明記される」という完了条件を満たすため。
- **請求集約元の明細行の描画には明示的な`rowHeight: LineHeight`を渡す**: `isHeader: true`のとき既定の`TableHeaderHeight`になり、改ページ計算のページ収容行数と食い違うため。

## 元帳・画面

- **元帳の残高は税込とし、消費税を独立した明細行として時系列に挿入する**: `tax_unit=1`（請求単位）の売上行は伝票時点で消費税額を持てない（CHECK制約）一方、入金額は税込のため、「売上`amount`の累計 − 入金の累計」では締め得意先の残高が税額分だけマイナスにずれる。請求締め済み区間は`billing.tax_amount`（確定値）を請求日の行、未締め区間は`ConsumptionTaxCalculator.CalculateExternalTaxBuckets`で仮計算した額を期末日付の行として挿入する。`tax_unit=2`は伝票ごとの`slip_tax_amount`をその伝票の直下に1回だけ挿入。`tax_unit=3`は`amount`が既に税込なので消費税行を作らない。
- **入金の残高影響は常に入金日付の独立行で発生させ、都度得意先の売上行の右側に出す「入金日付・入金No」は消込の証跡として表示するだけで金額を載せない（`ReceiptAmount`をnullのまま）**: 売上と入金が月をまたいでも各月末の売掛残高が日付どおり正確になり、月次締めの暦月末残高の定義と矛盾しないため。1つの売上明細行に複数の入金が証跡として紐づく場合、2件目以降は売上側の列を空欄にした行を直下に続ける。
- **消込の証跡（`LedgerReceiptPairing`）は表示専用で、残高計算に使わず、金額の按分を一切行わない**: 残高は`DetailReceipt.AllocatedAmount`を明細入金行ごとに独立行として計上する別ロジックが担うため、証跡に万一漏れがあっても残高は狂わない。明細請求書指定は連携するすべての売上明細行に証跡として結びつけ、どの明細行にいくら充当されたかの厳密な按分は行わない（`SettlementService`の配分アルゴリズムとは別物）。金額按分つきのペアリングにすると証跡ロジックが不必要に複雑になる。
- **繰越は全期間積み上げで算出し、`monthly_closings`や`billing.previous_balance`を起点に使わず、残高キャッシュ列を持たない**: 都度集計する方針（残高キャッシュ列を持たない）と整合させ、`billings`のスナップショットとの二重計上を避けるため。再検討条件: 性能不足の場合は残高キャッシュ列を追加する。
- **仮計算消費税は`ProvisionalTaxAsOf(customer, salesLines, asOf)`という日付の関数として定義し、期間境界（`PeriodFrom`の前日と`PeriodTo`）で差分を取る**: 固定の「期末に1行」にすると、期間Fromより前の未請求売上の税が繰越に入らず全期間積み上げと矛盾するため。
- **解除済みの請求データ（`billing_status=2`）は元帳の残高計算の対象外**: 「解除済＝集計対象外」の仕様のため。
- **元帳が正、`billings`は締め時点のスナップショットとし、両者の不一致を検出して例外を投げない**: 元帳は常に実データからの都度集計。締め後に過去日付の新規売上・入金を登録すると元帳の残高と`billing.current_billing_amount`はずれうるが、これは正常な業務オペレーションで起こりうるため（編集ロックは既存行の編集のみが対象で新規登録は防げない。請求締め分は日付制限で新規登録・日付変更自体を禁止して解消している）。
- **元帳はアプリ側のLINQで複数テーブルを取得してマージし、単一のSQLビュー（UNION等）にしない（SQLビューは使わない）**: マイグレーションを使わない方針と相性が悪いため。統合後は`sales`/`receipts`を`customer_code`で絞るだけで済む（内税明細単位は`sales`と`detail_receipts`）。あわせてナビゲーションプロパティを持たせず`Include()`を使わない。
- **元帳のマージ・時系列化・残高推移・仮計算税・消込証跡は、Application層でなくDomainの純粋関数（`CustomerLedgerBuilder`）に置く**: 残高推移が手計算と一致することをDB不要の単体テストで直接検証でき、月次締めが同じ関数を再利用できるようにするため。Application層（`CustomerLedgerQueryService`）はクエリして渡すだけ。元帳は`receipt_allocations`を一切参照しない（締め解除で解除済み`billings`を指す充当行が残留しうるが、元帳は参照しないため影響しない）。
- **元帳の1伝票の明細が請求済・未請求に分かれると`tax_unit=2`の`slip_tax_amount`が実態とずれうるが、元帳側に独自の整合チェックを入れない**: 請求締め時に`BillingClosingService.CalculateTaxSummary`が検出して例外を投げるため。元帳は照会画面であり、業務ルール違反の検出責務は請求締めが負う。
- **元帳の現在残高は本日時点の残高を検索期間とは独立に表示し、得意先確定時と表示(F5)の都度、実データから再計算する。ウィンドウ間の変更通知機構（イベント配信・SignalR・ポーリング等）を持たない**: 求めるのは「キャッシュ列に頼らず表示するたびに最新の実データから計算する」正確性の保証（残高キャッシュ列を持たない方針の帰結）であり、画面を開きっぱなしで他画面の更新を自動反映するリアクティブUIではない。アーキテクチャ上も、各ウィンドウは独立したDIスコープ・DbContextを持つだけで、ウィンドウ間でデータ変更を通知し合う仕組みは設計されていない。期間From/Toを変えても現在残高は連動しない。
- **伝票プレビューは専用画面を作らず、売上入力・入金入力・明細入金を読み取り専用（プレビュー）モードで開く。3画面の読み取り専用化は共通基底クラスを作らず個別に実装する**: 過剰な抽象化を避ける既定方針。プレビューは非モーダル・毎回新規ウィンドウで、新しいDIスコープ・DbContextで開くため常に最新DBを見に行く（元帳表示時点と食い違うのは正常な業務オペレーションとして許容）。
- **元帳の行から開く画面は行の種別で決める（売上→売上入力、消込証跡の継続行→明細入金、消費税行は伝票単位のみ売上入力、請求単位の確定額・未締め仮計算・繰越は開かずステータスバーに理由を出す）。入金行は得意先の`TaxUnit`が明細単位かで明細入金か入金入力を分ける**: `ReceiptSlipNumber`は`receipts`と`detail_receipts`どちらの番号かを区別する情報を持たないため、登録後不変の税区分で分岐する。消費税行のうち請求単位の確定額・未締め仮計算は辿れる伝票が無い。
- **プレビュー画面はEscで閉じられる（プレビューモードのときだけ）**: 保存・取消以外に退出手段が無いため。通常の編集セッションは未保存の入力をEscで誤って破棄しないよう対象外。
- **メインメニューは、メニュー構成マスタ駆動でリスト・アコーディオン型（C案）を採用し、ウィンドウは縦長（幅300、高さは作業領域に合わせる）とする**: 理由: 要確認（採用理由の記録なし）。
- **メニュー構成マスタの編集画面は、既存項目の表示名・表示順・必要権限レベル・初期展開だけを編集できる最小範囲とし（管理者専用）、項目の追加・削除と`screen_key`・親子関係の変更は`scripts/`のSQLへ直接記述する**: `screen_key`は`OpenMenuItemCommand`の`switch`に対応するコードが要り、項目は実装フェーズごとに増えるため、画面から自由に追加できるものではないから。メニューは実運用でも使う本物の構成データのため、開発用テストデータ（`seed_dev_data.sql`）とは別のSQLで投入する。
- **メニュー権限は子（末端の機能）のみに持たせ、親（分類の見出し）には持たせない（`CK_menus_leaf`でDBが強制）。表示できる子が1件も無いカテゴリは表示しない**: 親には遷移先画面も権限もなく、子には両方あるという構造のため。フィルタは`MenuService`でなくDomainの`MenuTreeBuilder`（純粋関数）の責務。社員マスタ・自社情報は機微な情報のため管理者専用とする。権限レベルの数値（管理者専用9・一般1）は暫定で、`scripts/`のSQL値を書き換えるだけで調整できる。
- **メニューの画面遷移は`screen_key`文字列を`switch`する`OpenMenuItemCommand`に一本化し、未知の`screen_key`は例外にせず警告メッセージを出す**: `menus`データの入力誤りに対する防御。

## 認証・監査

- **認証は起動パラメータで渡す社員コードのみとし、Windows 認証は併用しない**: ショートカットの引数を書き換えれば任意の社員（管理者を含む）になりすませるが、社内クローズド環境での簡易識別として容認し、認証強度は求めない。再検討条件: 管理者限定操作（請求締め解除・月次締め解除等）の実効性を担保する必要が出た場合は、Windows ログオンユーザー名と社員マスタの突き合わせを併用する（UI追加は不要で、ログイン画面なしの方針と両立する）。
- **操作ログ用の別テーブルは作らない**: 全テーブル共通の監査列（`created_by`／`created_at`／`updated_by`／`updated_at`。`*_by` は社員コード）と、請求データ・明細請求書・月次締めの確定・発行・解除・取消の日時＋実施者の個別保持で、締め解除などの権限操作も追跡できるため。
